# FX 读取重复调用与内存复用审核（2026-10-18）

本轮仅审核代码与已有profile证据，没有修改业务逻辑、缓存策略、数据库或接口。推荐先合并读取、复用当前请求/推送轮次里的已有对象，再单独设计共享价格读快照。账户资金、交易风控、封禁及应急停增险继续读取既有权威来源。

[上一轮profile](../output/fx-cpu-io-profile-20261017/report.md)显示，SQLAlchemy与异步调度是主要CPU类别。私人交易SSE路径约27%的CPU样本中，大部分落在调度、取消及发送，数据库操作只是其中一部分。因此不能认为给SSE增加缓存就能消除这27%。数据采样有扰动，以下次数推算不等于新的吞吐收益。

| 项目 | 减少数据库调用的做法 | 内存是否有用 | 本轮判断 |
| --- | --- | --- | --- |
| 依赖身份read_dependencies | 三个SELECT改为一次UNION ALL，仍由Python按product/id去重排序 | 当前请求内结果即可；不需要跨请求缓存 | 优先，局部改动 |
| 聚合接口认证、SSE定期准入 | 仅取id/is_active等实际字段，避免完整User ORM装载 | 不缓存封禁状态 | 优先评估，主要减CPU而非SQL条数 |
| 公开行情先锁ID再读Pair | 用一次SELECT完整Pair FOR SHARE，并复用已锁对象 | 同一事务内复用Pair即可 | 优先，仍保留共享锁 |
| 成交量和历史元数据 | 同一次读取带出volume、history_version、history_ready | 不需要建立新累计量缓存 | 优先评估回退与快照语义 |
| 私人pricing逐订阅者model_dump | 数据库本来按市场共享读取；此项减少重复对象转换 | 每一轮每个市场转换一次，复用只读字典 | 简单，但收益预期较小 |
| Registry保存上次市场定价 | 单纯保存_entries目前不减少查询 | 适合扩展为共享只读价格快照 | 有潜力，但需确认新鲜度及失效方案 |
| 用户依赖集合按经济版本缓存 | 命中时可跳过三类身份读取 | 有潜力；现有economic_version不足以覆盖全部清理路径 | 暂缓直接落地 |
| 账户余额、债务及风控缓存 | 不直接移除权威事务读取 | 仅限已锁事务内复用，不新增内存资金账本 | 保持既有权威边界 |
| FX历史运行时、公共SSE bytes | 已有K线ring和共享公共帧编码 | 已实现，不能重复计算为新收益 | 保留并明确能力范围 |
| 普通配置 | 冷缓存五次getter可用get_many批读 | 已有60秒进程缓存 | 低优先，热缓存本来就不查库 |

最适合先做的是以下几项。

1. **依赖身份三查合一。** `credit/trading_context.py:34`目前分别读LMSR市场ID、FX钱包pair_id、FX空头pair_id。versions、prices、私人SSE初始同步/15秒检查/account_changed都会调用；context已从basis复用，不再属于这部分重复。可以用带product标签的UNION ALL一次返回三类行，再沿用现有集合去重、排序和current_group补入。三张表仍然要读取，减少的是两次往返、语句构造和异步切换，不能声称扫描工作减少三分之二。

   必须保持零余额/零份额行，不套用risk.discover_dependencies的正余额过滤；LMSR仍使用Position INNER JOIN Outcome；FX与LMSR相同数字ID不合并；缺失市场仍进入原missing_groups处理；prices仍按认证用户依赖加当前市场授权。一次SQL取得身份的观察时点比原三个READ COMMITTED语句更集中，但并不自动产生完整账户事务快照。

   以既有profile约32.07秒的活跃分段为例，PG中此处独有的FxWallet.pair_id查询执行711次；3→1理论上可少1422次执行，约44次/s。按该次约1.59万cursor执行估算，约9%的执行数，不能直接当CPU或吞吐提升9%。这也是最适合作为下一次单项A/B的改动。

2. **投影读取身份，避免无用ORM对象。** `trading_user_id`和`stream_identity`只需要用户ID及准入检查，却调用get_current_user装载整行User；SSE周期检查只判断用户存在且is_active，却也读取整行。可在保持JWT类型/到期/用户不存在/USER_BANNED语义的前提下，研究共享身份校验与标量投影，减少字段解码和ORM装载。不能直接把其他需要User完整对象的接口一并替换，也不应复制一套JWT校验算法。此项通常仍有一次数据库查询，不应计为少一次SQL。

3. **公开行情事务内复用已锁Pair。** `fx/market_data.py:249`先SELECT pair.id FOR SHARE，随后`trading.get_public_snapshot`又调用_pair读完整Pair。同一个事务里可用完整Pair加共享锁，再把这个已锁对象交给快照构建逻辑，省一次重复读取。它仍是从数据库读取已提交状态，保留原来的共享锁与事务范围；不会要求新增价格缓存或移除一致性锁。

4. **成交量与元数据的共同输入。** `fx_volume_24h`已经在一个SQL快照内读取history_ready、durable cursor和分段成交量；`read_fx_snapshot_metadata`随后又读取同一份状态。可以评估让前一次读取同时返回history_version/history_ready，供快照构建复用。保持历史未就绪/缺失时的精确SUM回退及None/False语义。仅做这两项局部收敛，公共发布的这段常规读取就有机会从“锁ID＋Pair＋volume＋metadata”四次降为两次；HTTP snapshot则有机会三次降两次。runtime.catch_up等其他读取不在这个数字里，实际总数仍可能更高。没有做实施或A/B，因此不保证时间收益。

5. **复用本轮pricing数据。** `PricingPublisher.run`已经每市场只调用一次Registry，却在遍历每个订阅者时重复对相同group做model_dump。可以先按市场转一次字典，再按各订阅者的affected集合组装列表。共享内容只读，不混入账户数据，仍保留每位用户的订阅过滤；只复用这一轮的数据，没有跨轮失效问题。进一步共享整条编码帧会影响Subscription队列/编码边界，需要另外说明方案。本次profile中pricing后台直接CPU约1.9%，不能把整个私人SSE的27%都算作它的收益空间。

内存值得用在哪里，以及它目前缺什么。

**市场价格输入是最有价值的共享内存候选。** 同一市场的储备、费率、状态和价格版本，对所有观看用户相同。`PricingRegistry._entries`已经保存上次digest/data，但refresh_groups每次仍取锁、开session、查库、转换数据、计算hash和构造返回对象；目前它是版本比较状态，并非避免数据库访问的缓存。把它扩成已提交只读投影，可以让context、versions、prices及publisher复用同一组输入，不需要新增Redis或第二套资金账本。

不过，这需要先确定以下契约，不能只在refresh_groups里加一个`if key in cache: return ...`：

- 覆盖现金/融资交易、空头、强平、机器人、注撤资、费率/状态/归档/删除，以及LMSR成交、结算、自愈等全部相关写入。更新或失效只发生在提交之后。
- 同组正在执行的旧数据库读取，不能晚回来覆盖更新的内存投影。现有Registry锁只串行化读刷新；如果另加writer直接安装，必须解决这个顺序问题。
- 进程重启/epoch更换、未预热、市场不存在、删除后重建等场景要有明确读库路径；不能把“内存里没有”当作“数据库不存在”。保存普通数据或不可变投影，不长期保存绑定session的ORM实例。
- `as_of`表达数据实际观察时间，不能把旧快照包装成刚查到；minimum_group_stamps、revision、input_hash必须来自同一组真实输入。
- 现有通知是可丢hint。必须有独立的权威重读/周期校对，versions作为兜底不能永远返回与SSE相同的过期缓存。否则最后一次变更通知丢失后，客户端和服务端缓存都认为“没变”。
- context在账户基准之后取价格，缓存不能悄悄返回账户变更之前的旧池输入并声称满足原覆盖语义。缓存新鲜度、强制刷新入口以及提交更新时序需要一起确认。
- 先限定于展示和浏览器预估的读取。实际成交、授权和风控仍按当前事务校验；不把读投影提升为新的交易权威。

短时间TTL或合并同组同时到来的刷新也会改变“每次读取都取得较新已提交输入”的时序。例如，晚到请求可能复用一条在它到来前已经开始的旧查询；而当前实现会在拿到Registry锁后再查。故它们不是无需审查的严格等价替换。可以作为设计选项比较，但须明确允许多旧、何时强制读库，以及如何保留兜底。

**已有FX行情内存不能直接代替当前价格与精确24小时成交量。** `FX_MARKET_DATA.state()`只有history_version、history_ready、applied/durable_event_id；ring保存K线和小范围尾部，它没有完整的当前储备、费率、pool_version和交易状态。历史更新可以滞后于交易，已消费游标也不等于最新资金状态。精确24h窗口还会在无新成交时随时间移动、旧成交过期；当前fx_volume_24h保留分钟边界和未落库尾部的单语句精确聚合，不能简单用固定K线窗口求和替换。此模块头部也明确禁止把ring当作精确rolling volume的来源。

LMSR writer已有q_dec和状态，但那是writer的资金执行状态及自愈生命周期。若用于共享读投影，应复制已提交、非unavailable的普通数据，并覆盖b/状态/截止时间、已结算市场、启动和自愈；不能直接给调用方暴露可变MarketState或随意换成浮点q。

**按用户economic_version缓存依赖，当前还缺失效覆盖。** 这类缓存确实能避免没变的账户反复查三类身份，还可以从已通过before/basis/after复核的context中填充。但代码存在具体例外：`admin_fx.delete_pair`会删除零钱包/零空头行，未逐用户推进economic_version。依赖集合刻意包含零行，因此这种清理会改变集合，却不改变缓存键。不是说现有功能因此出错；这是准备新增缓存时不能忽略的边界。

如果以后选择这条路线，应缓存用户的基础依赖集合，current_group在每次请求中另加；先明确管理员清理、缺失实体、数据重置及版本生命周期怎么处理，保留周期权威核对，不让过期集合影响prices授权。仅复用某条SSE连接当前的订阅集合也不能自动解决这个问题。给每个用户增加一套常驻资金镜像或复杂恢复流程，当前没有必要。

这些部分暂时不改为只读内存：

- 实际成交的余额、债务、持仓及锁内版本/价格复核。已锁事务内的数据复用可以继续研究，长期内存资金权威属于更大的架构决策。
- 封禁、登录准入、JWT到期、应急停增险。原语义要求检查数据库或按既定周期核对，不能依靠可能丢失的通知维持永久缓存。
- `credit_new_risk_frozen`的热读明确绕过60秒TTL；不能为了省一次SQL把它与普通配置一起缓存。
- 15秒versions校对与私人SSE复核各有恢复和准入职责，不能因为读取重叠直接删除其中一个。先减少其查询成本。
- `my-trades`是独立的成交明细，snapshot有24h量/历史元数据，context没有这些全部内容，不能把成交后的所有请求都算作重复。

另外，公共BROKER已经把同一MarketEvent编码成共享bytes后分发，订阅表和队列本来就在内存；普通site_config也已有60秒缓存。不要为这些已完成的工作再加一套状态。`read_rules`冷缓存五项getter可改用get_many，暖缓存收益很有限。固定SQL结构/绑定参数也可减少重复表达式构造，不需要保存业务数据，但应先选高频路径量化收益，避免全面改写数据访问层。

推荐顺序：先做依赖三查合一、身份标量投影和公共快照同事务复用，逐项或按独立风险集中验证；可以顺手评估本轮pricing对象转换复用，但不以此解释27%的SSE CPU。随后根据混合压测结果，单独提交共享价格读投影方案，明确提交更新、覆盖与权威兜底。用户依赖长期缓存、资金内存化和取消公共共享锁暂缓。

本轮证据来自上述生产代码、已有profile的SQL/CPU统计及既有同步设计第8节；没有实施候选或运行新的性能/单元测试。普通局部收敛可沿现有架构落地；共享价格读快照及新增缓存失效/同步契约须先确认方案。没有提交、推送或部署。
