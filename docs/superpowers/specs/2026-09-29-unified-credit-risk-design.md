# LMSR 与多外汇统一贷款、净值及固定强平设计

创建：2026-09-29；修订：2026-09-30。状态：用户已确认简化方向，本文待审阅；未实施业务代码或开启生产功能。

相关资料：[参数准备](../../fx-margin-preparation.md)、[FX 现货设计](2026-09-28-fx-market-design.md)、[估值口径](../../holdings-value-semantics.md)。本稿替代上一版分来源贷款、分资产保证金和全局经济锁方案。

## 1. 已确认的产品选择

这是趣味游戏，不追求严肃金融市场模拟。用户明确接受 LMSR、摩拉、龙门币等资产统一风险待遇，也接受价格跳变导致爆仓。系统应简单、可解释；正确报价、账务一致和可恢复执行不能省。

首版采用：

- 一个现金余额、一笔金圆券总债务、一种统一贷款利率。
- 一个初始保证金门槛、一个维持保证金门槛；所有资产共用。
- LMSR 与多个 FX 持仓共同抵押；任一产品的损失可能导致其他产品减仓。
- 风控净值使用每个产品自己的真实清算算法，不能用边际市值替代。
- 固定排序、固定比例、逐批还债的强平算法，不做最优清算搜索。
- 保留现有按市场串行、不同市场可并行的执行能力；禁止新增覆盖全站经济写的互斥锁。

目标规模 50–100 人、每人初始 500 金圆券；摩拉初价 0.2 金圆券。最高 20x 是名义仓位/权益的目标，不是保证足额开仓。统一规则也适用于 LMSR，不增加专属折扣或风险分层来限制它；相应的穿仓风险是被接受的玩法取舍。

首版只做借金圆券买现货/份额的多头。不做外币借贷、裸空、永续、多贷款来源、多利率、抵押品相关性、压力保证金、保险基金或自动最优化。多个 FX pair 从本期开始支持，均以金圆券为计价和债务单位。

## 2. 最小数据模型与服务边界

### 2.1 保留现有权威

保留 `User.cash`、`User.debt` 和 `User.debt_last_accrued_at`，它们继续是现金与总债务唯一权威。复用现有 loan_service 的借还款、按经过时间计息和账本；不新增 CreditLiability、分来源还款队列或债务兼容投影。

保留 `Position` 与 `FxWallet(user_id, pair_id)`；外币数量按 pair 分开，不能把摩拉与龙门币相加。FX 钱包增加非负数量/成本约束。统一品种键为 `(product, id)`，不同产品同号不能共用行情、缓存或限流键。

新增内容仅围绕执行正确性：

- 用户经济状态版本与授信冻结标记，用于并发重验及坏账后禁止再借。
- 持久化 `LiquidationRun/Action`，每用户最多一个活跃 run、一个在途动作，唯一操作键防止重复卖仓和还债。
- 强平恢复依赖 `LiquidationRun/Action` 与下一次定时扫描，不新增风险 dirty 表或风险通知 outbox。

普通贷款流水记录原因和操作键即可，不按买什么资产分拆债务。风险参数修改记录审计版本，但不建立多套账户政策体系。

### 2.2 模块职责

- `loan_service`：现金/债务、计息、借还款和账本，所有产品复用。
- 统一估值服务：批量读持仓与品种快照、调用清算数学、合并净值。
- 统一风险服务：两条门槛、交易后风险检查、固定强平编排。
- LMSR/FX 执行器：各自报价、持仓及池状态变更；不复制贷款和风控规则。

接口保持小而明确：批量读取版本化快照、对一个市场的整组持仓计算清算回收、模拟指定数量动作、在调用方事务中执行指定动作。数学函数不查数据库；执行器不自行提交、不发送 SSE、不等待另一个 writer。

这是改造目标：当前 FX execute_trade 自行 commit 并广播，需拆出内部事务函数；不能直接把现有公开服务包一层用于强平。

## 3. 两种净值，统一口径

记现金 C、包含应计利息的债务 D、边际市值 V、净清算回收 L：

```text
展示净值 = C + V - D
风控净值 E = C + L - D
```

资产页、排行榜主数字保持展示净值，另显示“清算净值”及保证金状态。贷款额度和强平必须使用 E。删除上一稿的第三种压力净值和同步压力模拟准入。

### 3.1 必须保留的产品清算算法

- **FX**：按 pair 聚合该用户全部外币数量，使用当前储备模拟一次 `quote_sell`，扣适用卖出费用并按现有精度舍入。摩拉与龙门币分别报价后，回收金圆券相加。
- **LMSR**：按 market 聚合全部 outcome 持仓，在同一个 q 副本上按 outcome_id 升序模拟全部卖出，每一步更新 q、计算 cost difference 和费用；不能将每个 outcome 在未变化的原 q 上独立清算再相加。
- 清算费率使用对应产品普通卖出费率，强平不额外加罚金。这会改变既有 LMSR 强平免手续费行为，切换时须公示并更新测试。产品交易费可以不同，贷款风险门槛保持相同。
- 暂停而不可执行的资产 L=0，展示仍保留带状态的 MTM；确定性结算应收只在能立即兑付时纳入 L。暂停资产不让整个账户免于强平其他可卖资产。
- 回收向下、费用按产品现行规则量化；债务与现金保持六位 Decimal。复用现有 LMSR 数学，不借此要求重写整个 LMSR 数值内核。

L 是单个账户在当前市场状态下的回收估算，不代表所有账户同时退出能拿到相同金额。清算改变池子后，其他账户在定时扫描中重估，不产生额外触发任务。

## 4. 单来源贷款与两条门槛

```text
R_initial > R_maintenance > 0

有债账户增险后：E_after >= R_initial * D_after
强平触发：     D > 0 且 E < R_maintenance * D
强平停止：     D == 0 或 E >= R_initial * D
```

只有这两条保证金门槛，不增加每品种 IM/MM、债务底线 beta、压力闸或单独恢复门槛。初始门槛同时作为强平恢复目标，形成缓冲。D=0 时不做比例除法，也不强平现货。

示例：500 自有资金、9,500 债务、10,000 总资产，忽略费用且可完整回收时 `E/D=1/19≈5.263%`。若将最高杠杆配置为 20x，令 `R_initial=1/(20-1)`，保存名义杠杆 Leverage 并在计算中使用高精度倒数，避免把截断小数当精确边界。交易费及清算折损会使实际开仓额度下降。维持率必须小于初始率，具体值作为游戏运营参数，不在本文宣称某个数值安全。

旧 `loan_leverage_k` 表示债务/权益上限；兼容时 `k=1/R_initial`，不能将“20x”直接填成 k=20。新管理页只暴露一种杠杆含义，旧配置迁移后停止双向独立编辑。

### 4.1 借款与交易检查

- 借现金 x：同事务 C+=x、D+=x；权益不变。计息后当前 L 不变时，理论新增额度为 `max(0, E/R_initial-D)`，向下量化。实际执行仍按锁后状态验证。
- 用户借款后买 LMSR 或外币，都必须模拟指定订单后的 C/D/持仓/市场状态并重新算 E，满足初始门槛才提交。不能凭借款时通过检查就放任后续买入。
- 可提供“借款并买入”原子入口，但仅模拟用户指定的订单与借款金额；失败整体回滚。不在成交临界区搜索最大可开仓数量。
- 现金消费/转出必须检查扣款后的 E；已有“有债禁止兑换”规则继续保留。管理扣款等例外必须明示并审计，不能绕过风险状态更新。
- 有债风险账户的卖出与现金还款允许执行；卖出回款优先同事务还债。增险冻结期间允许充值、还款和清算路径。
- 无债且本操作不新增债务的交易仅做原有现金、持仓、市场检查，不计算全组合 LCV；不写强平 dirty 标记，不触发强平任务。

### 4.2 利息和坏账

统一利率，复用现有时间复利/六位量化逻辑；每次经济写先按统一时点结息，估值读包含尚未落库利息。利率变更必须先按旧率结算到切换时点，或使用有效时间段计算，不能把新率追溯套到全部历史。

强平卖完可执行资产后仍欠款：保留 `User.debt`，标记资不抵债并禁止再借；用户仍可充值还债。暂停资产待恢复再处理。管理员通过已有免债入口显式核销并记录坏账原因，不能默默清零，也不从 FX treasury 自动赔付。核销与未来授信解冻是两个明确动作。

## 5. 固定强平算法

采用全站固定比例 `liquidation_partial_pct`，初始沿用 10% 作为批次大小；不同产品不分别调参，不搜索“最优”卖出量。

### 5.1 定时扫描入口

本期仅使用定时扫描发现风险及续接未完成的强平。沿用 `liquidation_enabled` 和 `liquidation_sweep_interval_sec`：保留已有配置，缺省 600 秒，允许范围 5–7200 秒；本次不自动缩短线上间隔。管理员 run-now 保留，调用同一个扫描入口，不绕过开关、阈值和防重入保护。

扫描先批量读取 `debt>0` 用户及持仓、计算组合清算价值，再仅对越线账户和已有未完成 run 做锁内复检。每轮覆盖当轮候选用户，按 user_id 稳定分页；分页是内存/查询批量限制，不是每周期只查前 20 人。最多 3 个执行 worker，同账户每轮最多一个卖出批次。已有 run 在恢复到初始门槛前继续处理；新 run 只在低于维持门槛时创建。

扫描轮次不重叠：定时触发与 run-now 共用互斥，已运行则跳过并记录；错过的定时触发合并，不补发大量过期扫描。重启后下一轮从数据库重算，识别已提交动作，不盲目重放旧订单。交易、行情、利息、新闻、暂停恢复和注撤资均不自动启动或续接强平。

两次扫描之间允许风险继续恶化，这是用户接受的游戏规则。借款和增险交易的同步准入检查仍然执行，但只负责接受/拒绝当前操作，不启动清算。

### 5.2 每账户每轮执行


1. 计息并复检触发条件；若未触发则结束。已在强平中的账户按恢复目标判定是否结束。
2. 用当前可用现金尽量还债，更新风险；达到恢复目标或债务清零立即结束，不再卖仓。
3. 按**当前整组净清算价值从大到小**选择一个可卖市场/货币对；同值以 `(product,id)` 排序。此顺序可解释且确定，不计算候选动作收益排名。
4. 若 E>0，出售该组每个持仓当前数量的固定比例（默认 10%）；按产品最小数量单位向上量化并封顶。LMSR 组内按 outcome_id 顺序执行，FX 按六位数量。向上量化保证小仓位最终可清完。
5. 若 E<=0，改为本次选中组全部卖出；其余执行与记账规则相同，不额外引入紧急保证金率。
6. 卖出、费用、持仓变更、回款还债及动作记录在同一事务提交。
7. 提交后重新检查恢复目标；未恢复则保存 run 状态，下一次定时扫描再执行一批，不即时重排或另起清算循环。非正权益也遵循每轮一个选中组的全卖批次。

版本过期则重新报价；不使用用户旧 min_out 阻止强平。不设会永久挡住紧急卖出的固定滑点限制。无正回收、市场暂停或数据异常则记录阻塞原因、尝试其他可卖组；不能删除未卖出的持仓。

同一账户最多一个在途动作。每次成交只更新当前账户风险，不同步重算全体用户。没有动作可执行时记录原因，由下一次定时扫描或管理员 run-now 重试；不能沿用 30 分钟无差别冷却。

## 6. 性能与并发契约

### 6.1 移除全局经济锁

上一稿第 8 节的全局 EconomicCoordinator 互斥锁取消。保留 LMSR 每市场 consumer、FX 每 pair 串行更新；贷款协调只是服务职责，不是全站排队门闩。不同用户且无共同风险依赖的不同市场必须能够并发提交。

统一模式首版仍限定一个经济写进程，与现有内存 writer 一致。第二写实例需被启动所有权保护拒绝；实现若采用 PostgreSQL session advisory lock，使用专用非池化连接，连接丢失停止写入，不把它误称为有 TTL 的租约。只读实例必须显式关闭所有写调度器，不能凭名字认定只读。

### 6.2 有债账户的一致快照

不能用过期抵押价放贷，也不能只重验当前交易品种。具体执行协议为：

1. 在无数据库行锁时批量读账户持仓集合及用户经济版本，形成完整依赖品种集合。
2. 所有经济写路径使用同一**按品种**读写门闩：本次改变价格/状态的品种取独占，其他抵押品取共享，按 `(product,id)` 全序获取，重复键合并为独占。不持有门闩等待另一个 writer 命令。
3. writer 命令先入队，consumer 内才获取所需门闩；FX 和直接贷款入口同样遵循。取得门闩后才进入数据库事务、取产品行锁（需要时）→ User → 持仓/钱包 → treasury 的稳定锁序。
4. 用户锁内重验经济版本和持仓集合；如不一致，回滚并释放全部门闩，重新发现依赖，禁止持锁补拿更早排序的品种。重试有上限，超限安全拒绝并提示重试，不能使用旧快照强行放行。
5. 核对整个组合的品种、持仓、费用/配置版本；未变部分可复用清算缓存，只重算变化组及指定交易后态。按当前时间加入应计利息。
6. 提交后在释放相关品种门闩前更新无 IO 的市场镜像；异常标记该品种不可增险，释放无关资源后仅隔离重载该品种。禁止因一市场 candle flush/恢复阻塞全站。

无债快路径只需目标市场独占门闩与用户锁；锁后若发现其他操作新增债务，则退出重走有债路径。还款只需用户锁且必须更新经济版本。修改账户资产、现金、债务的全部路径均更新该版本。市场 tick/状态/注撤资都更新品种版本并遵守品种独占门闩。

此协议保留独立市场并行，但共享抵押品仍存在必要竞争；大量跨市场持仓会扩大锁集合。实现必须证明 writer、结算、配置变更与门闩顺序不存在循环等待，并通过 PostgreSQL 并发测试。若验证或性能门槛未过，不得退回全局锁后宣称性能不变。

### 6.3 估值与后台工作上限

- 版本化估值缓存键包含用户持仓版本、品种价格/状态版本和费用版本；快照批量读取，禁止每个持仓单独查询。缓存服务正确性依赖版本，不依赖 TTL 猜测新鲜度。
- 交易不写强平 dirty/outbox，不展开有债持仓用户。定时扫描批量加载用户、持仓和市场快照，分页初始 20 人，每轮遍历全部候选；禁止每个用户单独加载全套公共行情。
- 每轮最多 3 个执行 worker、每用户一个在途动作及一个卖出批次；复用现有 writer 有界 FIFO，不新增 1:1 加权公平调度。已完成批次不立即重新入队，剩余风险留待下轮。
- 批量估值适时让出事件循环，记录扫描耗时、实际覆盖人数、执行数、跳过数和错误数。扫描超出周期时记录告警并跳过重叠轮次，不因为“超过 3 秒”自动全站停借。
- 排队不占数据库连接，不持用户锁。未开始的命令安全取消后可返回拒绝；已可能提交的命令只能返回结果未知并允许操作键查询，不能统一当作 429。
- FX 引擎按 pair 短事务；行情发布与成交量计算放到提交后后台，成交响应不等待 24h 全量交易记录拉取。多 pair 之间不能互相延长事务。

### 6.4 性能验收是比较结果，不是保证口号

DSH 审查发现上一版存在全局串行、交易后任务扇出、嵌套模拟及恢复阻塞风险，本版移除对应设计。审查没有运行性能测试，不能据此宣布“无性能下降”，也不采用报告中未经测量的吞吐推算。

实施阶段先对改造前基线和新实现使用同机器、PostgreSQL、数据集、请求轨迹、连接池及负载进行对照。至少 5 轮、统一预热，保存每轮和汇总；不得通过增加拒单或降低负载改善延迟数字。

- 无债原有交易：P95/P99 延迟增幅目标不超过 5%，成功吞吐下降不超过 5%，错误/超时率不得显著上升。此 5% 是工程容差，不宣称数学上零开销。
- 既有 single-writer 文档目标仍保留：buy P50<20ms、P99<200ms、quote P99<50ms、峰值>300rps；这些是验收目标，不是已实测事实。若基线本就未达标，单独列为既有问题，不能用它掩盖新回归。
- 新信用路径独立报告估值计算、SQL 次数、门闩等待/持有、数据库事务和端到端时延；必须覆盖同账户跨品种及不同账户独立品种，证明后者未被全局串行。
- 100 用户、多个 FX、LMSR、系统 tick、PvE 与批量强平并发下，其他正常交易仍满足上述相对回归门槛；监测事件循环延迟、连接等待、拒单率和队列深度。
- 测量完整扫描耗时、覆盖全部候选的时间、每账户锁内复检时延、跳过轮次数及固定批次执行时间；100 用户基准下完整扫描 P95 应小于配置周期。不再设置事件到风险复检 3 秒 SLA，也不以此自动冻结增险。扫描间隔及多轮分批导致的延迟须如实展示。

不符合门槛时先修执行瓶颈，不自动放宽旧性能目标。当前只完成文档设计，没有执行上述验收。

## 7. 多 FX、展示与状态

解除管理端“一次一个 trading pair”的限制。摩拉、龙门币各有独立池子、treasury、目标价、事件与版本；贷款利率及保证金门槛仍是全站唯一配置。新币种不需要新增贷款类型或强平策略。

行情 broker/缓存/序号/限流使用产品命名空间，修复同号 market_id/pair_id 混发。外币按 pair 返回持仓与金圆券估值；统一账户 API 返回 cash、debt（含利息）、display_equity、liquidation_equity、E/D（无债返回 null）、两条门槛和风险状态。

区分暂停开仓与暂停所有交易。reduce_only 允许减仓/强平；halted 不成交。暂停 FX 系统干预不等于暂停用户风险减仓。人工撤资可能造成风险变化，须展示影响，强平重估由下一轮扫描承担；接受游戏风险不代表允许负储备或不记账地改池子。

UI 明示统一抵押与跨产品强平。风控响应不公开 FX 隐藏目标价和事件冲击参数。页面验证遵循用户偏好，以截图为主，不自动点击或填写表单。
