# FX 到价挂单设计

日期：2026-10-14。状态：用户已授权按本 spec/plan 实施，采用 Sol low 执行、Sol medium 审阅；本稿所列推荐规则随整体实施授权确认。任何新增算法、功能或超出本文的架构选择必须先向用户报告。旧计划中的每轮 50 张上限由本次全量价格条件扫描提案取代。

## 基本原则

### 前端下单与挂单执行共用成交逻辑

玩家点击交易按钮与 scheduler 触发挂单，都向同一套 FX 成交业务逻辑提交玩家授权的交易指令。池子报价、自动借款计算、跨零多空处理、风险检查、资金结算、成交回执、审计和提交后的账户/行情更新均复用，不为挂单维护另一套算法。

两种入口负责的工作不同：前端入口处理登录身份、即时操作和报价确认；挂单入口检查触发条件、读取已保存的授权、校验订单状态、记录结果及通知。共用成交逻辑不要求 scheduler 调用 HTTP 接口，也不要求两种入口的请求参数和通知完全相同。

把交易指令与执行参数分开。例如“买入 1,000 金圆券，允许最多自动借 600”保存的是玩家意图及授权上限；实际借款额由共用逻辑在执行时按最新账户、回补及锁金释放计算。平仓指令同样在执行时解析实际持仓，不把挂单时的预估数量当作最终数量。这些计算留在成交业务层，不分别放到前端和 scheduler 中实现。

### 共用资金逻辑，明确事务所有者

事务内成交核心负责计算和写账，不自行 commit/rollback，不在提交前发布 SSE。普通下单入口提交成交及回执；挂单入口将成交、回执和挂单成功结果一起提交。两者提交成功后都沿用现有账户和公开行情更新；挂单额外发送本人结果通知。

本原则要求局部调整现有成交函数的事务接缝，不授权通用交易框架、大范围重构或修改既有定价、费用、借贷和风控规则。已存在的不提交资金助手优先直接复用。

### 按当前规模实现

采用一张挂单表、现有单写实例和定时扫描，不预留资金、不建设撮合簿。明确失败结束并通知，玩家可查看原因后重新挂单；理论故障风险不自动扩展成新的恢复状态机、请求队列或额外数据表。

## 目标与已确定规则

玩家用填空句子描述动作：

> 当〔币种〕汇率〔≥ / ≤〕〔触发价〕时，〔买入 / 卖出 / 平仓〕〔交易规模〕。

- 每个玩家全账户共 3 个有效挂单槽位，所有 FX 币种共用。
- 不预留现金、外币持仓或借款额度。挂单后玩家可以继续正常交易。
- 无到期时间；持续等待直到触发处理或主动撤销。挂单保存在数据库，玩家离线也能触发。
- scheduler 定时扫描，默认 10 秒，间隔作为管理员配置项。
- 只按扫描时的当前行情判断，不追溯两次扫描之间短暂碰到的价格。
- 触发价只是触发条件，不是成交均价保证。不增加用户滑点容忍度或成交均价限制；价格影响由玩家自行估计并调整触发价。
- 满足条件后尝试交易；明确失败就结束，不等待玩家补充资金后再成交。
- 成功、明确失败都通过本人私人 SSE 发送结果通知，仅在已有交易页面连接中接收。
- 结果写入挂单记录。离线或断线后能查看记录，不新增离线通知中心或消息补发系统。

## 动作与规模

买入允许回补后开多、卖出允许卖出后开空、平仓只减仓已确认。下表中的平仓比例、固定平仓方向和触发时持仓范围已随完整设计获确认；买入指定外币数量、卖出指定金圆券金额暂不加入。

| 动作 | 输入单位 | 触发时的含义 |
| --- | --- | --- |
| 买入 | 金圆券金额 | 先回补空头，剩余金额开多，沿用现有统一买入语义 |
| 卖出 | 外币数量 | 先卖掉多头，剩余数量借币开空，沿用现有统一卖出语义 |
| 平仓 | 指定方向持仓的百分比，默认 100% | 根据触发时指定方向的实际持仓计算，只减仓，不反向开仓 |

买卖的金额/数量在挂单时固定，不随行情自动改变。平仓比例针对触发时的持仓，包含挂单后同方向增加的部分；方向在挂单时明确为多头或空头，不能因为后来反向开仓而平掉另一方向的新仓。

不增加买入指定外币数量、卖出指定金圆券金额两种输入模式。平仓无对应方向持仓时结束，记录“已无对应持仓”，不生成零金额成交。

### 自动借款

买入默认不自动借款；玩家可明确开启并设置金圆券借款上限。触发时只借实际不足的部分，超过授权上限或不满足授信/风险要求则失败。例：买入总额 1,000，借款上限 600，可用现金 800 时借 200；可用现金 300 时所需 700 超上限，失败。

多空跨零时按现有结算语义计算实际资金缺口，不能只用总买入金额减去挂单时的现金。空头回补和锁金释放先按现有规则处理；自动金圆券借款只能作用于现有允许融资的新多头段，不扩展回补融资规则。

卖出允许借外币开空，提交挂单前说明这一授权和可能产生的外币债务；继续接受国库实际库存、借币开关和账户风险检查，不新增外币借贷额度机制。平仓沿用现有减仓及回补规则，不开启新的增险融资。

## 已确认技术路线

### 模块与依赖

沿用 FastAPI、SQLModel/PostgreSQL、Vue 3 和 APScheduler，不新增依赖、独立服务或部署组件。

- `backend/app/services/fx/orders.py`：挂单创建/查询/撤销和结果记录。
- `backend/app/services/fx/order_scheduler.py`：扫描与生命周期，调用挂单业务层。
- 现有 FX 成交模块：普通下单与挂单共用事务内成交核心，继续拥有池子、账户、借贷、钱包、成交回执及审计的实际资金逻辑。
- 现有私人 trading SSE：增加挂单结果事件；前端沿用现有通知组件。

现有 `execute_net_trade` 入口会 rollback、末尾会 commit，不能在外面先锁订单再直接调用。推荐从 `net_trading.py` 提取最小事务内核心，现有网页包装器继续负责原来的事务、重试和提交后发布；挂单包装器复用核心并增加订单状态处理。空头回补优先复用已有 `execute_short_cover_in_session`，不复制回补账务。具体函数签名和局部改动范围写入实施计划，未经确认不扩成通用编排框架。

### 存储与接口

推荐增加一张 `fx_trigger_order` 表及普通增量 Alembic 迁移，保存归属用户/币种、条件方向和价格、动作及方向、金额或比例、自动借款授权上限、状态、时间、失败原因及成功回执引用。订单结果保留在同表，不增加通知表、申请表或通用订单系统。

价格、金额和数量沿用现有十进制精度；比例单独校验。成功关联现有 `FxExecution`，回补使用现有可核对的成交结果。不得增加新的未审计资金写入。

推荐本人接口：

- 创建挂单；服务端验证完整参数、玩家身份/币种可见性和槽位。
- 查询本人有效挂单及分页历史。
- 撤销本人等待中的挂单。

第一版修改挂单采用撤销后重建，不新增修改接口；所有接口只允许操作本人数据。3 槽限制复用 user 行锁下的计数检查，不创建单独槽位表。

历史保留币种标识。市场删除政策推荐“存在挂单历史则拒绝删除，使用归档”，这样保留普通外键且不增加快照/置空处理；此政策已随完整方案获用户确认。赛季重置清空挂单，再按现有依赖顺序清理成交及回执，避免新外键阻断清理或旧单执行到新赛季；business reset 沿用新 head 建库及非保留业务表为空的验证，不新增挂单重置子系统。

### 行情与扫描

推荐使用玩家图表/行情的同一价格定义：池子储备比值的公开六位小数 `price`，不是买卖带费率的 `buy_price` / `sell_price`。条件包含等号。

每轮批量读取有效单和所需币种的当前价格，按挂单 ID 顺序处理。先做轻量条件判断，条件满足就尝试成交，并记录扫描观察到的触发价格。进入成交边界再次校验挂单状态、用户、市场和风控，实际报价采用锁内最新储备；不因成交前行情回退而把已经触发的单改回等待。这符合“扫到条件就尝试交易”的规则，先执行的其他订单可能改变后续单的实际成交价。

沿用唯一写实例和 `max_instances=1`，没有公开手动扫描入口。不引入撮合簿、价格事件队列、分布式任务或资金预留。批量价格读取结束读事务后，逐笔进入独立写事务；每笔释放锁后处理下一张，不持有覆盖整轮扫描的事务或全部池子/账户锁。

已确认不增加市场暂停或 FX 交易总闸关闭的自动等待例外：仍可读取可靠行情且条件满足时，挂单失败并通知。挂单入口必须明确检查并拒绝，不能假设现有成交核心必然拒绝；当前普通交易的部分暂停状态仍允许减仓，保留其既有行为。这是挂单触发后的执行限制，不另建资金规则。无法读取可靠行情时本轮不判定触发。市场删除/归档导致订单永久不可执行则结束并记录原因；此永久不可用处理已随完整方案获用户确认。

### 成交与结果的一致性

按照前述共用成交原则，把挂单成功状态/回执引用和真实成交放在同一个数据库事务提交，复用现有 gate 集、锁序和资金写入助手；现有网页直接成交的资金规则保持不变。

锁序沿用 GATES → pair → User，在 User 锁后、资金写入前锁挂单并重查等待状态，后续钱包/空仓/国库锁沿用成交核心。创建用 User 锁下计数及插入；撤单用 User → order，不持有 User/order 锁再申请 pair gate。撤单与成交只有一方能成功；资金回滚后记录失败也要重新锁定并校验订单状态，不能覆盖已成功撤单的结果。

动态借款金额、持仓比例和账户版本由共用业务逻辑在锁内当前状态下确定。新多头段按回补及锁金释放后的可用现金计算借款缺口，再校验玩家上限及现有风险要求。空头比例平仓先按现有逻辑结息，再取比例；100% 采用 `cover_all`，内部金额边界来自同次锁内最新报价，不沿用过期网页报价上限。

即时网页请求仍保留现有账户版本及成交保护；长期挂单保存授权指令，不保存旧网页版本作为未来执行前提。两种入口各自解析已授权指令后进入共用核心，不靠关闭网页账户版本校验来实现复用，也不把挂单无均价限制的规则扩展到普通下单。

明确业务拒绝回滚资金变更，再记录挂单失败。每张挂单使用稳定请求编号关联现有成交回执；未知提交结果先读取订单及回执核对，不换新编号重做，不把“结果未知”显示成明确失败。无法读取数据库时停止本轮并记录日志，恢复后的处理仍须先核对。具体请求身份绑定和异常退出行为在实施计划中明确；本文不授权新增持久化待核对状态、恢复队列或通用请求恢复系统，若现有回执与同事务状态不足以满足核心要求，另列决策点确认。

必须保留的实际不变量是：撤销成功的订单不能随后成交；成功挂单对应真实已提交成交；同一挂单不能产生两笔独立操作；失败不能留下部分跨零成交。相关永久测试仅填补这些新增真实行为的覆盖缺口。

### 私人 SSE 与界面

推荐新增 `fx_order_result` 私人事件，携带订单 ID、币种、动作、成功/失败、实际成交摘要或失败原因和结果时间。成功后同步账户/持仓；任何终态后更新挂单列表。不得把私人订单、借款或失败信息放到公共 FX 行情流。

结果持久化后才发通知；通知失败不改变成交结果。复用现有本人订阅队列，不新开 SSE 连接。挂单成功的 `account_changed` 保留账户刷新，通过专用 reason 跳过通用账户提示，由 `fx_order_result` 展示一次成交结果；失败没有资金变动时只发送结果事件。不新增跨事件去重框架。切换账户仍遵守既有身份隔离。

UI 在 FX 交易页面提供填空表单、有效槽位计数、有效挂单列表及结果记录。动作联动输入单位；借款项只在买入显示；平仓显示方向和比例。页面文案明确“到价尝试交易”“不预留资金”“触发价不保证成交均价”。视觉布局沿用现有组件。

## 范围与验证

本轮不做限价均价保证、部分成交、自动反复重试、到期、修改订单、离线推送、事件强平或内存权威 FX writer。扫描间隔可配置，不承诺每张单严格在 10 秒内成交，也不追溯停机期间触价。

实施前确认新增表/接口/模块及成交事务衔接。相关现有检查集中执行；新增测试集中在实际挂单行为、真实数据库事务及必要的私人事件隔离，避免跨层复制。页面最多截图，不进行浏览器自动点击/填表/交易流程。没有新的常驻压测框架或大型 CI 流程。

本文保存已确认的设计；实施检查见[验证记录](../../fx-trigger-orders-validation-2026-10-14.md)，尚未部署。
