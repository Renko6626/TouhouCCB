# LMSR 内存行情读取与行情恢复方案

状态：**延期待办（2026-10-12）。** 用户短期不实施，要求保存后续任务。阶段 1/2 的推荐方案保留，产品代码未修改；FX 内存 writer 继续仅列待办。恢复执行前仍需确认下文的新模块、存储和初始化方案。

## 目标和当前事实

在 `feat/fx-net-trading` 的 `4893853` 清理结果上继续性能与结构优化。

- writer 的 q、prices、status 已常驻内存，近期 ring 与 tick 也在内存。
- 市场列表、详情和 SSE 首包仍从 SQL 份额计算当前价；首包随后从 ring 取历史尾段，存在跨读取时刻拼装的问题。
- `writer_ops` 在成交提交后计算 N×4 条 candle；`market_writer._apply_outcome` 更新 ring、合并 flusher 缓冲，完成后才结束该指令。
- candle 批量落库目前没有持久消费游标，启动用近期窗口清重建。FX 已有独立行情整理与持久进度机制，可借鉴其职责和可靠性协议。

阶段 1 统一当前行情读取。阶段 2 让交易 writer 专注经济状态，把行情聚合、批量保存和恢复交给 LMSR 行情服务。定价、账务、风控、审计和每笔 SQL 提交保持现有语义。

## 阶段 1：统一只读市场快照

### 推荐边界

新增 `backend/app/services/lmsr_market_reads.py`，只负责复制、读取和投影市场快照。保留现有 `services/lmsr.py` 数学模块，不建立同名目录包。

`MarketReadSnapshot` 为不可变值对象，包含 market_id、按 ID 排列的 outcome_ids/labels、q_dec、8 位价格、b、status、closes_at，以及行情覆盖水位。构造时复制 tuple/值，不把 `MarketState`、可变列表或 ring 直接交给 API。

`read_live_snapshot(market_id: int) -> MarketReadSnapshot | None` 在一次无 await 的读取中复制相关字段。若 writer 停止、state 缺失或 unavailable，返回 None；调用方按端点职责处理，不把不可用的活跃状态当作正常价格发布。

### 读取规则

- 写 owner 的可用活跃市场：当前份额、价格、status、b、closes_at 使用同一份内存快照。
- SQL 提供标题、描述、tags、起始份额、胜出选项、结算字段和用户准入信息；阶段 1 不复制成另一套长期目录缓存。
- 只读实例和重启前已结算的市场：保留 SQL 读取。历史段超窗也保留 SQL；这些是读取职责，不恢复非 writer 经济写实现。
- writer 开启且活跃 state 异常：明确拒绝该行情读取，避免用 SQL 掩盖 state 故障；已订阅流的异常遵守现有重连机制。
- 列表、详情、SSE 首包复用同一投影规则；不改变响应字段、金额精度、排序、过滤、分页和权限语义。
- 首包的当前份额/价格与历史尾段水位一并捕获。查询 SQL 元数据后重新取得快照，不在等待 SQL 前保存可变 state 引用。
- SQL 元数据与内存快照必须校验生命周期一致性：比较相关 status、b、截止时间及结算字段完整性，不能拼出“已结算状态 + 尚未读取到的胜出/结算信息”。不一致时结束旧读事务、刷新 SQL 实体后有界重读，仍不一致则拒绝本次响应。不能用同一 session 的陈旧 identity-map 数据反复重试；阶段 1 不默认新增版本字段或 schema。
- SSE 保留先订阅取得 anchor、再构造 snapshot 的顺序，以及 trade_id 去重；不删除心跳、gap 检测或断线重连。

### 预期收益与边界

减少当前价格的重复计算和数据来源分叉；若端点仍需 SQL 元数据，不能宣称整个端点零 SQL。阶段 1 不优化 24h 统计、成交活跃度聚合、用户持仓读取或 FX 报价。

## 阶段 2：独立行情整理和持久进度

### 方案取舍与推荐

| 方案 | 好处 | 代价 | 判断 |
|---|---|---|---|
| 只搬出 candle 计算，保留近期窗口重建 | 改动较小 | 没有持久处理边界，故障恢复仍靠窗口和重建 | 可作局部优化，但未完成本阶段恢复目标 |
| 独立 LMSR 行情服务，持久游标与 K 线同事务提交 | 能明确补齐缺口，处理重复/提交结果未知；交易与行情职责清楚 | 新表、首次建基线、首包衔接和生命周期调整 | **推荐，实施前确认** |

经济状态仍由原 writer 维护，FX 经济写结构保持不变。LMSR、FX 各自拥有行情服务，不将两个产品强行改成通用交易引擎。

### 文件和依赖方向

- 新建 `services/lmsr_market_data.py`：按市场串行消费已提交数据，维护 ring、内存处理水位和可靠待写范围，提供快照尾段/历史读取。
- 新建 `models/lmsr_market_data.py` 与 Alembic 迁移：保存 `LmsrMarketDataState`（建议表名 `lmsr_market_data_state`）。
- `writer_ops.py` 保留经济事务，不再计算 candle_rows；返回已提交成交/市场变动的轻量标识。
- `market_writer.py` 提交后更新 q/价格/状态，非阻塞通知行情服务；保留实时 tick 成交与状态投喂。不等待 candle 聚合、SQL 扫描或 flusher。
- `history_ring.py`、`candle_writer.py` 保留已有编码与纯计算，阶段 2 的行情服务调用它们。
- `candle_flusher.py` 改为带市场范围和持久游标的可靠批次。可以借鉴 FX 的批次/不确定提交协议，不扩大成跨产品通用框架。
- HTTP 层依赖只读快照/行情读取接口；行情服务不导入 API、不调用交易 writer、不持经济门闩、不写资金或持仓。

### 持久化与恢复协议

建议每市场保存 `market_id`、`last_transaction_id`、`history_version`、`history_ready`、`updated_at`。内存另保存 applied/queued/durable 水位和必要的上一份完整价格向量；持久水位只在 candle 保存事务提交成功后推进。

- SQL 中已提交的 `Transaction` 是追赶依据；提示可以合并或丢失，周期检查补偿。游标按市场的成交 ID 推进，不能假设全局 ID 连续，也不能用墙钟时间作为唯一处理边界。
- 消费和分页须保持同市场的经济执行顺序，预检现有历史是否满足 ID 顺序/完整快照契约；成交数值从真实生产记录重建，不根据当前余额猜历史。
- 普通买卖按现有规则生成全市场四档 candle。处理强平记录时更新价格上下文，但沿用“强平只推价格、不新增普通成交量”的现有产品语义；结算不凭空计入成交量。
- 第一份价格从 `Outcome.initial_shares` 与 b 得到，后续结合已存价格快照和真实成交前价确定向量；非均匀初始价、强平插入和缺快照必须可明确重建。重建不确定时停止并报诊断，不使用均匀 1/N 或局部价格凑完整向量。
- 一个批次保存 `(expected_cursor, through_cursor]` 的增量和 history_version；candle 与新持久游标在同一事务提交。
- 重复批次根据持久游标判断已应用；游标断档/版本不符拒绝。提交结果未知时先读检查点，禁止把同一批 volume/n_trades 再累加一次。
- 保留有界 ring、分页和合并提示，处理循环分批让出事件循环。行情积压不增加经济交易的等待；读取未完成历史时明确拒绝或重试，不能返回空历史冒充完整。

### 首次建基线与上线方式（待确认）

Alembic 只建立进度表，不自动删除历史 candle。首次启用前，在停止经济写的维护窗口，按市场用真实交易离线建立基线：保留现有数据备份；每市场重建 candle 与对应 cursor 在同一事务提交，失败整市场回滚。分页处理，先预检历史来源完整性和规模，记录预计维护耗时。

预检失败不进入写服务；历史不能确定重建时先修复来源，不清空图表。首次基线完成后，正常重启只读取已保存 candle 并补齐 cursor 之后的缺口，不再每次删除近期桶。空市场须单独初始化为 ready。

历史重建须对比已有已封存段：若内容变化，实施前确定已有 immutable HTTP 缓存的失效办法；不能在旧 URL 下继续提供被缓存的错误段，也不能未经确认改变公开 URL/响应契约。history_version 用于服务内部的代际判断，不能假定它已存在于当前 LMSR 历史 URL。

完成切换后移除旧窗口重建及重复行情落库路径；不保留 legacy/new 运行开关或两个同时累加的管道。离线修复工具可以保留，运行职责要明确。

### 实时首包与历史衔接

拆分后，writer 的当前状态与行情 ring 可能处在不同处理水位。SSE 首包不能直接拼“最新价格 + 落后的 ring”。

- writer 快照包含已提交的市场变动/成交边界；为普通成交去重提供覆盖 ID。
- SSE 先取得 broker anchor，在读连接窗口内捕获当前快照边界 N；行情读取把 tail 补到 N 后再生成完整首包，水位和 tail 一起返回，图表跳过已包含的成交。
- 返回的 tail 必须截至 N，不能已经包含 N 之后的成交。同市场 consumer 若已超过 N，聚合桶通常无法反向截断；此时重新捕获当前经济快照与历史覆盖边界，取得一致首包，不能只修改覆盖 ID。tail 和水位复制为不可变结果，防止 consumer 在 await 之后继续修改已选中的数据。超过重试/等待预算按连接阶段拒绝或关流重连。
- 补齐不持经济门闩、用户锁或 writer 队列，也不修改经济 state；限制单次工作量与等待时间。发响应头前预检不可用状态；生成器内补齐失败按现有方式关闭流并重连，不能发送虚假的完整快照。
- 不可变历史段须满足封存、处理完成和持久进度覆盖；落后时不允许缓存不完整的 200 响应。
- 新市场注册、归档/结算历史、writer 自愈和优雅停机均走明确生命周期。自愈读取 SQL 恢复经济 state，行情服务独立从持久检查点恢复。

### 性能验收

分别记录交易响应、writer 队列等待、SQL 次数和行情追赶延迟。同输入比较，保留资金/份额/审计与 candle 字段核对。移出聚合可能增加行情 SQL 消费或事件循环负载，不承诺吞吐提升；若没有减少 writer 的实际等待或使总负载明显恶化，停止扩大改动并保留证据。
