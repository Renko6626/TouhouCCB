## 1. 目标与已确认原则

玩家输入金额或数量时，浏览器根据最近收到的账户与行情状态，直接模拟整笔交易及账户风险，不因每次输入或每条行情重新请求服务端报价／全账户估值。

- 进入页面先取得完整交易账户基准：现金、持仓、债务、锁金、计息时点和风险规则。
- 行情通过 SSE 持续同步，浏览器本地更新持仓价值、净值、保证金预警和订单预估。一个连接承载多个品种；五个 FX 品种的储备更新无需五个独立连接。
- 账户发生实际变化时，通过仅本人可读的事件展示必要提示，并触发一次完整账户刷新。短时间多次变化合并刷新。
- 本人操作的成功响应与对应账户事件共用刷新协调器，避免重复成功提示和重复刷新。
- 后端在真实成交时继续读取权威状态、模拟、风控、检查价格保护并原子入账。浏览器结果不作为资金或授信权威。
- SSE 是同步提示，不承担资金提交的正确性；事件丢失由重连与低频校对恢复。

用户已确认上述行为方向。下文新增接口、模块边界及数值实现是技术建议，不把讨论中的一般认可扩大为对全部技术细节的授权；进入实现前确认第 11 节。

补充确认（2026-10-12）：用户确认采用专用交易账户基准聚合 API。初始加载、成交后恢复和账户变化通知共用一次完整基准刷新；聚合现金、债务、持仓、锁金、规则及依赖定价基准，整体校验安装。K 线、成交历史、称号等独立读取，旧接口保留；后端直接批量读取和复用只读逻辑，不在内部串调旧 HTTP 接口。具体路径名、认证流传输和数值实现仍按下文提案确认。

精度补充确认（2026-10-12）：用户选择本地预估按当前 6 位小数金额／仓位精度处理，不追求超过现有业务精度的预估。沿用后端各步费用／产出舍入，比例、已有费率／定价参数和中间运算不提前截成 6 位，否则会改变最终六位结果；不改变后端既有字段精度。算术实现仍优先复用现有工具，无必要不引入依赖。

## 2. 现状及范围

LMSR 的 `TradingView.vue` 已用 `utils/lmsr.ts` 在本地计算成本、所得、均价和滑点。当前市场 SSE 最多约 8Hz 合并推送价格；其他市场定价上下文随 `fetchSummary()` 的市场列表请求刷新，未持续订阅。`user` store 的统一净值、风险等级和可用现金仍取服务端账户快照；没有周期账户轮询。本人成交先本地应用现金／仓位，再刷新 summary；gap 与长时间隐藏后回到前台也刷新账户。

FX 的 `/net/quote` 当前读取池、User、当前钱包、国库、全部本人短债；有债增仓进一步检查全组合。FX 页面单独拉 snapshot、summary、wallet、short、my-trades。报价腿虽含储备，公开 snapshot/SSE 尚未持续提供完整储备与费率。

版本现状：LMSR 没有可直接复用的持久价格 revision，现 broker seq 只表示已发布消息的顺序，不能证明数据库／writer 的所有定价变更均已覆盖。FX 旧公开帧可用 publication 的 post_price 覆盖另一次 snapshot 读取的价格；新交易预估流不得将这个旧 price 与最新储备拼成一组数学输入，应从同一已提交快照派生价格。保持旧图表兼容不意味着它可直接充当新定价基准。

本期主体为 FX 常规统一买卖的本地预估、跨产品账户风险重估、交易账户同步与私人提示。LMSR 抵押品纳入组合估值，既有 LMSR 本地报价与价格保护保留；LMSR 页面采用同一账户同步／风险状态，避免同账户两套同步逻辑。旧全部回补快捷操作保留纯平仓语义；它的预估也使用本地含息欠币与 exact-output 数学，不保留必须先请求 short quote 的前置条件。旧 API／pending 请求恢复保持兼容。

不包括：限价单、交易算法或费率重写、FX 内存权威 writer、LMSR 行情持久恢复重构、事件触发强平、离线通知中心、多写进程／新消息总线、全站 UI 重做。

本期展示当前及模拟成交后的净值、保证金／风险等级和距既有门槛的余量。多资产账户的单品种“爆仓价格线”需要额外确定其他资产不变、储备如何随价变化等假设，本期不承诺求出唯一爆仓价格，也不伪造固定线。

## 3. 三种状态与时间

1. **账户基准**：本人已提交的现金、金债、全部 LMSR／FX 仓位、短债、成本、锁金、经济版本。仅账户变化或恢复同步时替换。
2. **定价状态**：当前交易品种及全部抵押／欠币品种的最新完整数学输入、状态、规则版本、市场版本与时间。随行情／运营参数变化更新，不携带其他玩家信息。
3. **派生预估**：按以上基准及估计服务器时间算出的含息债务、各组价值、汇总风险和订单后态。输入、行情或时钟变化时本地计算，不写回账户基准。

“最近收到”不是所有市场在同一时刻的原子快照。每个组保存版本和 `as_of`；账户保存 `economic_version`、`as_of`，连接有重启可区分的 epoch。乱序／旧响应不能覆盖新状态，跨 epoch、缺组、断线或规则不明须显示待同步，不沿用旧的“健康”判断。

报价参考价、执行均价、价格影响及订单后态必须从同一份目标品种输入计算，避免现在从本地行情取参考价、再拿另一时点服务器报价比较的问题。

## 4. 账户读取契约（聚合方向已确认，字段与版本契约为提案）

新增已认证的 `GET /api/v1/user/trading-context`，供首次加载和账户事件后的大刷新使用。它返回交易所需原始状态，不附带称号、成交历史、排行榜、24h 成交额或 K 线，不以完整 summary 全站对象作为长期预估输入。

它是专用聚合读取接口：一次请求得到可整体替换的交易基准，服务层直接批量读取既有模型和只读投影，复用现有数学／规则，不在内部发 HTTP 拼接 summary、wallet、short 等旧路由，也不重复执行每个旧接口的完整估值。一次响应仍可包含数条必要 SQL，不把“一个 API”宣传成“一条 SQL”。现有 summary／wallet／short 路由继续为旧页面／客户端服务，不因新增聚合接口进行全站迁移。

交易页的初始加载、本人成交后恢复及私人账户事件共用同一聚合刷新入口；仅行情变化不调用它。刷新先完整校验响应及版本／依赖覆盖，再整体安装，不能逐项成功回填造成现金、欠币和仓位分属不同快照。历史、图表和界面辅助数据的刷新独立，不妨碍账户基准安装。

金额、份额、储备、费率、利率、门槛参数使用十进制字符串；ID／版本使用经过安全范围校验的整数或不丢精度的字符串。包括：

- User：现金、持久金债、计息时点、经济版本、信用冻结及最近强平标识。
- LMSR：按 market/outcome 分组的本人数量和成本。
- FX：全部正钱包数量／成本、空头本金／已计利息／计息时点、锁金、收益基准。
- 规则：日利率、LMSR 卖出费率、名义杠杆 L、维持参数 m、交易／借款／新增风险开关与规则版本。
- 当前交易品种及全部账户依赖组的定价基准和版本；即使某组停牌也要返回其状态，不能漏掉后假装价值已知。
- `as_of` 与服务器时间，用于估计时钟偏差及统一计息时点。

账户行、仓位和债务必须属于同一可验证经济版本；不能把旧现金与新仓位拼接。读取方案需在执行计划中固定：推荐读取前后复检经济版本并有限重试；经济版本覆盖不到的写入口先补齐，不能依赖一次版本比较掩盖缺口。各市场快照可异步新鲜，但每个组内的储备、费率、状态与版本必须一致。

账户基准还必须附每个依赖组的最低定价版本／覆盖水位：context 所带定价基准须至少覆盖产生本次账户基准的已提交市场变化。推荐先读取账户基准，再读取各组已提交定价输入，最后复检账户版本；不读取旧缓存假装满足该下限，不为此新增账户与逐笔市场变更的映射表。浏览器应用的行情版本至少达到这些下限，且依赖完整，才能宣布账户同步完成。这样成交后的仓位不会配上成交前的池／q；其他不影响账户基准的后续市场变化仍允许异步新鲜。事件到达先使账户失效，版本下限随大刷新返回。

大刷新默认更新上述全部账户状态和所需依赖组，并调整订阅集合。已在浏览器的更新行情若版本更高继续保留，不能被较旧 HTTP 定价基准覆盖。成交历史需要时单独刷新，不阻塞账户恢复。

## 5. 单连接行情与私人事件（建议）

推荐新增已认证的 `GET /api/v1/user/trading-stream`，一个交易会话内合并公共定价组和本人账户事件。现有图表公开 SSE／历史接口保留；当前品种行情在前端有统一 owner，避免两个流互相覆盖或重复聚合成交。

服务端从认证用户推导私人主题，不允许客户端指定任意 user_id。依赖组来自本人账户及当前交易品种；账户刷新后，前端重建连接／订阅集合。首期可用重连调整集合，不为此引入 WebSocket。认证采用现有 bearer 机制，使用可带 Authorization 的 fetch SSE 或短期流票据二选一；不把长期 access token 写进 URL。

私人流有界队列、慢消费者断开和连接结束清理；凭证到期须重新认证，退出、停用或权限失效不得无限保留私人订阅。复用现有限流和连接生命周期模式，公共与私人 topic 不可互相订阅；认证失效不清除结果未知的 pending 请求身份。

### 5.1 定价消息

- FX：pair ID、金／外币储备、买卖费率、status、reduce_only、archived、pool_version、`as_of`。
- LMSR：market ID、按 outcome ID 排序的完整定价向量及份额输入、b、status、closes_at、价格／参数版本、`as_of`。定价与组清算精度契约见第 6 节。
- 规则：版本与完整影响预估的规则输入；利率、费率、杠杆、维持线、冻结开关变化也使预估失效或重新计算。

定价消息按品种合并；一个品种更新只使对应组估值和依赖它的订单失效。高频帧不触发账户 HTTP。完全静止品种不靠“多久没成交”判为过期；连接心跳／订阅覆盖确认用于证明仍在同步。

成交外的注撤资、费率、状态、截止时间等变更也必须推进定价版本并发布或显式失效，不能只监听成交。广播只读已提交输入、共享物化消息，不能为每个订阅者重新跑完整账户估值；网络推送不留在资金事务／独占门闩内。

### 5.2 本人账户消息

最小事件：`account_changed`，包含 `event_id`、`economic_version`、`reason`、`occurred_at`、可选安全业务关联 ID。提示依据 reason 映射自然文案；刷新后的账户才是金额／仓位来源。

覆盖：本人或其他客户端成交、借还款、强平实际资金动作、管理员调账／免债／信用冻结、市场结算、兑换／消费等会改变交易基准的现有入口。计息时钟／债务落库变化也不能漏同步，但合并为静默事件，不每次弹提示。规则变化使用规则消息，不伪装成私人余额变动。

强平分阶段提交时，事件只描述已完成的实际动作；不能在第一次减仓就声称全部强平完成。逐次实际变化都可使账户失效，提示可合并为“账户发生强制减仓，正在同步”。

事件由真实事务拥有者在 commit 成功后轻量排队；不在 `bump_economic_version()` 内直接广播。rollback、失败、幂等成功回放不新增账户事件或成功通知。推送故障不改变资金结果。

一期不新建永久通知表或 outbox，不保证离线收到全部文案。保证恢复账户当前状态，不能把临时 SSE 当持久事件日志。进程崩溃导致 commit 后通知未发的窗口由第 8 节兜底。

## 6. 本地数学与风险语义

### 6.1 FX 整笔模拟

复现现有 net 规则：反向先平仓，超出再开反向；用第一段后储备算第二段，不把两次手续费／舍入合成一次。

- 卖出：先卖自有外币并优先还金债，再为不足部分模拟借币开空、所得锁金。
- 买入：先回补统一时点的含息欠币；完整回补用 exact-output，预算剩余才买多头。
- 本仓锁金只用于本仓回补，其他空头锁金不得消费；显式新金借款只用于新增多头，不能融资填回补缺口。
- 保留全部卖出／全部回补的纯平仓意图、只减仓规则、六位精度、dust 拒绝与存储范围。
- 返回各腿投入／产出／费、整笔最低所得或最高回补支出、最终方向、现金／债务／锁金变化、自动还款和订单后风险。

本地可判断已知的余额、仓位、冻结、状态及保证金条件；国库实时可借库存等未同步信息标明“提交时检查”。不为追求完整 executable 布尔值扩大公开国库信息；本地状态区分“已知条件满足”“已知条件不满足”“数据待同步／条件未确认”，避免承诺必成交。

### 6.2 全组合风险

采用后端现有整组清算规则：FX 多头卖出净额、FX 空头全仓含息 exact-output 回补成本、LMSR 同市场各 outcome 按 ID 顺序在滚动份额／价格副本上卖出。不能直接复用 `computeHoldingsValueLcv()` 的逐仓独立求和充当权威公式。

令 C 为现金，A 为正资产可清算总值，D 为含息金债，K 为全部空头含息回补总成本，L 为名义杠杆，m 为维持参数：

```text
E = C + A - D - K
W = max(L * D, (L - 1) * A) + (L - 1) * K
B = W / L
增险条件：L * (L - 1) * E >= W
强平预警：存在金债或欠币，且 L * E < m * W
```

风险比较用未量化 E/W，展示再舍入；不拿四舍五入后的 E/B 判边界。无债务不显示强平风险；停牌组、截止市场、欠币不可完整回补、缺失快照等沿用后端现有价值／未知规则，不自行把未知 K 置零。现金可用性还须独立扣除全部锁金。

同时保留并本地更新两种净值，不改变既有字段含义：`display_equity = C + MTM_lmsr + MTM_fx - D - 边际空头债`，账面价仍计入有合法定价输入的 HALT／paused 持仓；`liquidation_equity = E` 使用上述清算口径。边际空头债与完整回补成本 K 不可混用；任一负债缺少有来源的边际估值，账面净值也必须未知。本金倍数输入继续取清算净值，保证金和预警只取清算口径；现有页面账面净值／浮盈不被 E 覆盖。具体暂停／结算组的 MTM 规则复用 `credit/valuation.py`。

区分当前风险和订单后风险。纯减仓的允许条件沿用原服务端语义，不能因为当前风险等级不健康就一刀切禁止回补／还款；新增风险才检查既有初始门槛与冻结。

### 6.3 计息与数值

按统一估计服务器时间 T 使用现有 `(1 + 日利率) ^ (elapsed / 86400)`，含息金债与欠币复用同一口径。单次模拟所有腿取同一 T，新本金从 T 起息，不改后端实际计息算法。浏览器时钟回拨／休眠恢复后重新校时，不累乘每秒已舍入债务。

FX 输入／输出使用十进制字符串，费用向上、产出向下及既有 exact-output 舍入必须一致。LMSR 现有 log1p/expm1 浮点预估可复用，但不能用被截断到 0/1 的价格反推完整清算风险；缺少可用输入时显示未知。

本地预估的 6 位金额／仓位精度已确认，不重复询问。算术实现优先复用现有 BigInt 定点／有理数基础及 LMSR 浮点工具；实施前以现有逐步舍入规则核对六位结果，利息／LMSR 非线性误差不作为升级业务精度的理由。确需新依赖或额外 q 定价字段时再提交具体取舍，不擅自安装。边界附近存在无法确认的偏差时标为“接近门槛，提交时确认”，不能人为放宽门槛。已有后端只读报价保留为诊断／兼容，不是每次输入的必经路径。

## 7. 前端同步与通知协调器

统一交易会话管理账户基准、组定价状态、连接和刷新；页面消费计算结果，不各自建立账户轮询。

- 首次订阅先取得账户／行情覆盖锚点，随后装载基准并按版本合并排队事件。HTTP 与 SSE 交错不能漏掉初始化窗口里的成交；具体首包／锚点契约实施前冻结。
- 收到更高经济版本立即使旧账户的“可新增风险”判断失效，再合并触发大刷新。同版本重复消息不重复刷新；事件文案按 event_id 去重，不能仅因某版本已刷新而丢掉此前未展示的强平／管理员通知。
- 一个账户至多一个刷新在途，记录目标版本；响应版本低于目标时不能宣布同步完成，随后补刷新，不能为每个版本并发启动请求。
- 本人成功响应先确认成交，随后和 SSE 事件复用相同刷新任务。不因刷新失败把成功交易报成失败，不将原成功请求换编号重发。
- 账号切换／退出废弃在途请求、旧事件、所有私有基准和订阅；跨账号不得展示旧通知或复用待恢复订单。
- 已提交但结果未知的原订单仍按既有 pending 参数／编号恢复；账户事件不能代替成功回执，也不能凭通知判断一笔未知订单已完成。
- 新行情到来更新预估；不会自动扩大已确认融资、纯平仓意图或滑点容忍度。实际提交使用当前展示并确认的预估生成 min_out/max_gold_in、expected_economic_version、allow_growth 等现有保护。
- 账户恢复后按新的依赖集合补订阅／退订；删除的仓位不再参与估值，新持仓未拿到定价基准时保持未知。

推荐事件合并窗口 200ms，本地行情重估合并到浏览器绘制帧，计息显示约每秒更新；这些是实现建议，后台标签页允许节流，恢复前台必须先校对。

## 8. 丢事件、断线与低频兜底

账户事件和行情都是可丢推送，因此仅有序号 gap 不足：最后一次 commit 后没 enqueue 时没有后续序号能揭露丢失。

- 每次重连／连接 epoch 变化、回到前台后核对账户与规则版本；必要时大刷新并重建市场基准。
- 推荐活跃页面每 15 秒执行一次轻量版本核对，只读取／返回当前 economic_version、规则版本、会话覆盖状态／服务器时间，不运行全账户估值。没有变化不全拉；隐藏页停止周期检查，回到前台立即核对。
- 同用户多标签页的合并是可选后续优化，一期不能依赖跨标签通知作为唯一正确性机制。
- 定价流必须有缺帧恢复、共享定价缓存失效与覆盖确认；不能只靠账户版本核对发现他人成交造成的漏行情。建议轻量核对同时确认所订阅品种版本／覆盖水位，落后仅补缺失定价基准。这个工作不执行组合估值。
- SSE 无法连接时显示同步中／行情可能过期；允许查看最后数据和手动刷新，禁用依赖未知输入的新增风险确认。纯减仓保留旧入口按权威服务端处理的途径，不改变其业务准入。
- 重试有界退避，不因刷新失败每帧发请求；网络恢复自动重建状态。

15 秒兜底只约束正常连接下的校对节奏，不保证网络断开时在 15 秒内恢复。无关行情变化不会拉账户，账户版本核对也不是实时逐 tick 查询。

## 9. 模块职责与性能边界（建议）

| 职责 | 建议位置／依赖方向 |
| --- | --- |
| 完整交易基准与轻量版本读取 | 新服务 `credit/trading_context.py` 与已认证 user API；读取既有模型／规则，不调用交易 wrapper |
| 组定价快照、变更消息 | 既有 FX publisher／market_data 与 LMSR writer/tick 接入；仅只读投影，不建立另一套权威池 |
| 私人变化提示与合并 SSE | 新 `services/account_events.py`、已认证流路由；事务 owner 提交后通知，不让底层数学模块发布 |
| 纯本地 AMM／净额交易模拟 | 新 `utils/fxSimulation.ts`，复用现有字符串／定点工具；不依赖 store、HTTP 或页面 |
| 组合估值／风险与计息 | 新 `utils/tradingRisk.ts`，复用 LMSR 数学和既有风险口径；输入显式，输出可检查 |
| 会话状态、版本合并、刷新协调 | 新交易会话 store／composable；调用 API／纯函数，页面和通知组件消费 |
| 页面接入 | FX、LMSR 交易页与风险提示；旧 API／图表协议保持兼容 |

不得按持仓用户数在资金事务里同步扇出，或给每个行情订阅者查一遍 User／全组合。无需新数据库业务表、框架、Redis、独立服务或部署拓扑。涉及重要模块边界和新增认证传输，确认后才实施。

性能目标：同一账户基准下，连续修改输入／收到行情不产生 net quote 或 summary 请求；一次行情只重估变化组并汇总，服务端计算主要发生在首次读取、实际账户变化、轻量兜底和真实成交。一次包含五个品种更新的包不产生五次账户读取。具体时延／CPU预算由实施前小范围基线固定，不在未测量前承诺吞吐。

## 10. 验收与验证范围

复用已有 FX、LMSR、credit、user store 和请求恢复夹具。永久测试只覆盖新增实际行为／资金风险缺口，不在各层复制整套场景。

- 同账户不变时，多品种行情变化正确更新当前风险和订单后风险；价格暴跌穿线即显示预警，不请求账户／报价。
- 平多跨零开空、回补跨零开多、纯平仓、融资用途、手续费／dust／舍入与含息边界，对照固定生产算法结果；LMSR 同组多 outcome 滚动清算，不独立求和。
- 200ms 内连续账户变更、刷新期间更高版本、重复／乱序、首包初始化交错、账号切换：最终基准达到目标版本，无重复交易和跨账号数据。
- 成交后账户配上成交前定价时保持待同步，直到全部组达到 context 的最低覆盖版本；账面／清算净值在停牌和空头回补成本有差异时仍分别展示，不互相覆盖。
- FX 发布排队期间又发生成交／注撤资／参数变更时，新交易流同帧参考价、储备、费率及版本来自同一已提交快照；不能拼接排队时的旧 post_price。LMSR 的定价版本不能只覆盖已广播成交而漏掉状态、b、截止时间或自愈变化。
- commit 后才通知；rollback、回放不通知；通知发送失败不影响资金提交。强平阶段性事件文案准确，其他经济变更入口覆盖清单可审阅。
- 模拟 commit 后通知遗漏、最后一条行情丢失、规则更新、连接 epoch 改变、后台恢复：轻量校对发现并恢复，不只测有后续帧时的 gap。
- 未知结果请求保留编号与纯平仓／融资意图；账户事件不解锁未确认交易。未知估值不显示健康，服务端实际交易保护不放宽。

默认运行相关已有后端检查、前端 unit／type-check／只读局部 ESLint／build。必要时隔离 PG 验证账户读取与提交通知竞态；不使用业务数据库。UI 最多必要截图，不自动点击、填表或执行真实交易。文档阶段只做内容、代码契约核对和 diff 检查，不将历史测试通过当作本功能验收。

## 11. 实施前确认的技术决策

1. **传输与接口**：专用交易账户基准聚合 API 的范围和共用刷新方式已确认，无需重复询问。`trading-context` 的具体路径／字段、轻量版本读取，以及单个已认证多品种／本人事件 SSE 仍为技术提案；保留旧公共图表接口。主要收益是完整数据、少连接和集中同步，代价是新增流协议、认证客户端与读模块。
2. **定价字段边界**：本地 FX 预估需要持续提供储备／费率；LMSR 完整组合清算需要可靠完整定价输入。只开放这些明确数学／状态字段，不开放国库余额、其他玩家资料或管理员运营参数。确认在认证交易流／context 提供，旧公开帧不自动扩大白名单。
3. **数值实现**：本地按现有 6 位金额／仓位精度处理已确认，无需重复询问。优先现有 BigInt／浮点工具，保持逐步舍入规则；若评估确需新依赖，先提供具体取舍再确认，不能默认装库或声称全算法逐位一致。
4. **恢复节奏**：200ms 事件合并、15 秒活跃页面轻量校对、每秒本地计息已获用户确认；作为代码常量及文档注释，不新增后台可配置项。提示首期不永久保存。
5. **页面覆盖**：推荐 FX 完成本地整笔预估，LMSR 复用现有报价并接共享账户／组合风险同步，不扩大成两套独立交易引擎或全站重写。

用户批准完整 spec 后再写实施计划，固定各阶段接口、数值误差与覆盖清单，创建／确认隔离工作区；本次不启动实现，也不改变既有延期项目状态。

定价版本的具体来源也须在计划前冻结：FX 核实所有相关写入口的 pool_version 覆盖，LMSR 另确定覆盖份额、b、状态、截止时间和自愈恢复的 revision／输入身份方案，并明确可比较组版本、epoch 及 HTTP/SSE 覆盖的对应方式。不能仅将 broker seq 或 last_ring_trade_id 改名为完整价格版本；不默认增加持久字段或改变数据库模型，确需迁移时另行提交取舍并确认。
