# FX 子游戏设计（2026-09-28）

## 1. 目标与已确认的玩法

在现有 LMSR 预测市场旁新增独立的外汇交易页面。金圆券仍是现有预测市场、借贷和兑换消费使用的现金；玩家也可用它兑换一种幻想乡虚构货币，再兑换回来。第一版只开一个金圆券计价的货币对，不做外币间直兑、做空、杠杆或限价单。

玩家应能通过报价、买卖、滑点、点差、平常噪声、定性新闻和成交记录理解汇率交易。宏观事件是主要的有方向波动来源；快速解读新闻并交易可以赚取有限的后续价差。玩家自身订单会改变汇率。少量黑天鹅由管理员创建，幅度和初始冲击通常大于普通新闻。

玩家只能看到市场报价、图表、成交量、新闻文案和自己的资产。内部宏观目标价、事件数值冲击、系统未来订单、随机过程状态不进入公开 API 或 SSE。内部目标价是此游戏的模拟变量，不宣称现实 FX 存在唯一的公允价格。

现有 `User.is_bot=true` 的 PvE 机器人账户不能调用 FX 成交接口；`quant/` 不接 FX API。平常噪声由 FX 引擎使用系统储备产生，不创建新的 User 机器人账户，也不扩展现有机器人策略。

## 2. 范围与系统边界

- 新模块独立于 `services/lmsr.py` 和预测市场的 `Market`、`Outcome`、`Position`、`Transaction`。复用现有认证、`User.cash`、`Decimal(16,6)` 资金精度、FastAPI、SQLModel/Alembic、审计与页面设计系统。
- 数据结构支持日后增加更多“金圆券 ↔ 外币”货币对，但第一版管理端只允许一个处于 `trading` 状态的货币对。外币名称和代码由管理员在开市前设定；开市后不可修改。
- FX 总闸默认关闭。管理员必须先建立货币对、设置初始汇率、向池子和系统储备注资，再开闸。交易暂停时允许查看资产、行情与新闻，不允许买卖。
- 所有 FX 资产都是站内虚拟数值，没有真实货币进出或外部汇率数据依赖。

独立表包括 `fx_pair`（池子、隐藏目标价、状态）、`fx_treasury`（系统两币种储备）、`fx_wallet`（用户外币数量与成本）、`fx_trade`（玩家与系统成交）、`fx_event`（草稿、计划、已发布、已取消、已完成状态）。站点级默认参数使用现有 `SiteConfig`，但每条事件把发布所需参数快照写入 `fx_event`。走势图由 `fx_trade` 中的成交后汇率按时间桶汇总；不复用 LMSR 的 Outcome K 线。

## 3. AMM 与成交金额

一对货币拥有真实记账的池子储备 `G`（金圆券）和 `F`（外币），均严格大于零。边际汇率 `P=G/F`，单位是“金圆券／1 外币”；无手续费成交保持 `G×F=k`。这些数值由数据库持久化，不能只存在内存中。

玩家投入 `g` 金圆券买外币时，手续费 `fee_g` 划入系统储备，净投入 `n=g-fee_g`，获得 `out_f=F×n/(G+n)`；池子更新为 `(G+n,F-out_f)`。玩家投入 `f` 外币卖出时，外币手续费 `fee_f` 划入系统储备，净投入 `n=f-fee_f`，获得 `out_g=G×n/(F+n)`；池子更新为 `(G-out_g,F+n)`。手续费在输入币种中收取，公开配置为每侧费率；它产生买卖价差。手续费向上量化到 6 位、输出向下量化到 6 位，余量留在池中；手续费不得吃掉全部输入，禁止零输出和非正储备。系统噪声与宏观干预按相同 AMM 公式成交，但手续费为零，避免系统向自己收费。

报价接口返回当前池版本、投入、手续费、预计产出、成交后边际汇率和有效成交汇率。执行时在数据库事务内重新报价，要求客户端传入最低可接受产出 `min_out`；池子变动后若达不到该值则拒绝，不按过期报价成交。池子行锁先于用户行锁，资金、外币钱包、池子、系统储备、成交记录及审计同事务提交。每个用户的幂等键唯一并绑定请求参数，同键重试返回原成交、同键不同参数拒绝；广播在提交后发出。

管理员通过显式注资／撤资操作调整池子深度，不能直接修改 `G` 或 `F`；撤资不得使储备低于安全下限。系统储备对两种货币分别记账且不得为负。初始注资是明确记录的站内虚拟货币发行，后续系统交易和手续费都必须守恒、可追溯。

## 4. 平常波动与宏观事件

货币对内部保存一个隐藏的宏观目标价 `A>0`。没有新闻时，`log(A)` 每 30 秒增加一个均值为零、标准差按时间平方根缩放的随机步进；默认小时标准差 `0.2%`，每步绝对值最多 `0.1%`。系统储备还会不定时通过同一个 AMM 池发出小额、双向的噪声订单；等待时间按平均 30 秒的指数分布抽取，单笔投入不超过输入币种池子储备的 `0.01%`。随机方向独立抽样。管理员可配置这两个强度、交易频率及系统每日支出上限。每个货币对在开市前设置目标价下限与上限，默认分别为初始汇率的 `0.5` 倍和 `2` 倍；普通漂移与事件冲击均被此区间截断。随机步进与订单落库以便审计；测试可注入固定随机源。噪声不直接改写池价。

系统的“宏观干预”也是有记录的池子交易：比较池价与当前隐藏目标价，向目标方向交易。无事件时，每个 tick 默认消除剩余对数价差的 `1-exp(-ln(2)×dt/600)`（600 秒半衰期）；有活动事件时，使用该事件窗口 `W` 的 `1-exp(-ln(20)×dt/W)`，即在无玩家干扰且预算充足时，窗口结束约消除首轮之后剩余价差的 `95%`。每 tick 同时受 `0.5%` 的默认价格变动上限、每日资金预算、事件预算及实际储备限制；上限由管理员配置。双向系统订单都按成交前汇率折成金圆券名义金额扣预算，即使该订单实际收入金圆券也消耗预算。玩家订单会改变价差，因此也会改变后续系统订单规模；玩家已把价格推到目标附近时，系统不继续同向买卖。任何预算耗尽或储备不足都让系统停手、记录原因并通知管理端，绝不生成负余额。

管理员事件含公开标题和定性正文、内部有符号冲击幅度、首轮反应比例、后续反应窗口秒数、事件干预预算、普通／黑天鹅标签和可选计划发布时间。普通事件首轮反应比例默认 `0.25`、窗口默认 `180` 秒；黑天鹅默认分别为 `0.7` 和 `180` 秒。管理员可以在创建事件时覆盖。管理端校验窗口 `30–1800` 秒、首轮比例 `0.1–0.9`、普通冲击绝对值不超过 `5%`、黑天鹅不超过 `20%`。默认值属于 FX 配置，可热更新；已创建事件保存参数快照，不受之后改默认值影响。

发布事件前检查系统储备与事件预算至少能执行一笔非零的首轮干预；不足则保持未发布、向管理员报错。发布时，隐藏目标价先受该事件冲击；同一事务中系统按“首轮比例”朝新目标价做一笔受预算约束的干预，然后提交事件和新池状态。提交后在同一 FX SSE 帧广播新闻和新报价，漏帧时客户端从快照接口恢复。余下价差在事件窗口内由定时 tick 按上述公式渐进消除；预算与玩家订单可能使实际终价偏离目标。快速反应者可在后续干预前交易，但新闻不公开冲击幅度或确定的未来成交价。事件窗口结束后回到平常干预速度，未完成的目标价仍作为后续宏观状态。

第一版每个货币对同时最多一个处于反应窗口的事件。计划发布的事件不得与已有计划窗口重叠；管理员手动发布遇活动事件返回冲突，可选择在活动窗口结束后发布。已发布事件不能编辑或撤销，紧急情况用 FX 总闸暂停。这个限制避免两条新闻的隐含冲击和预算相互覆盖。

## 5. 管理端与调度

`/admin/fx` 提供：创建和启停货币对、初始及后续储备注资、费率和噪声配置、预算和价格变动护栏、事件草稿、立即发布、定时发布、取消未发布事件、查看系统储备与干预日志。事件详情区明确区分“公开新闻”和“仅管理员可见的数值参数”。所有写操作只允许超级管理员，校验范围并记录操作者与前后状态。

计划发布时间以 UTC 存库，管理页面按浏览器本地时间显示。调度器每 5 秒扫描到期事件和 FX tick；数据库中的事件状态与锁是唯一权威来源，进程重启后恢复。手动发布与调度发布调用同一幂等服务，并以数据库行锁或条件更新保证同一事件只发布一次。调度失败保留待重试状态和错误日志；已经提交的首次干预不会重复执行。FX 总闸关闭时，不发布计划事件、不执行噪声及系统干预；重新打开后，逾期事件按原定时间顺序逐条发布，前一条活动窗口结束后才发布下一条，管理员可先取消未发布事件。

前端新增玩家 FX 页面：当前有效买／卖价与价差、价格图、定性新闻流、兑换表单、外币持仓与历史成交；显示预估产出和最大滑点。管理员新增 FX 管理页。遵循现有黑白工业风，页面验证遵循用户偏好：默认截图检查，不做浏览器自动点击或表单流程测试。

## 6. 资产、借贷、排行榜、审计和赛季

玩家买外币扣减 `User.cash` 并增加 FX 钱包数量；卖出反向处理。外币钱包记录数量与金圆券成本，FX 成交单独存表。FX 市值按最新 AMM 边际汇率显示，首页、资产页、财富榜及称号净值统一使用 `cash - debt + LMSR_MTM + FX_MTM`；FX 盈亏单独展示，避免混入预测胜券的盈亏说明。消费榜维持原有口径。玩家无法把外币直接用于预测市场、兑换商品或还款，须先卖回金圆券。

第一版 FX 外币不计入借款额度与强平抵押物。`debt>0` 的账户不能买入外币，但能卖出外币取回金圆券；借款发生在持有外币之后时，现有借贷计算仍只看金圆券现金及预测市场持仓。FX 行情不会直接触发对 FX 持仓的强平。前端明确标注“外币资产计入展示净值，不计入借款抵押价值”。

FX 买卖、系统噪声、宏观干预、注资、配置修改和事件发布写入可重放的交易／审计记录。扩展现有资金审计折叠逻辑，让 FX 造成的 `User.cash` 变化可核对，且外币钱包、池子和系统储备有独立守恒检查。公开接口和 SSE 只序列化白名单字段，不暴露隐藏目标价或未发布事件参数。

赛季重置在停服事务中清除 FX 钱包、成交、池子、储备、事件和相应审计，并关闭 FX 总闸；新赛季由管理员重新建立货币对、注资开市。保留既有兑换核销记录的规则不变。

## 7. 错误处理与验收

- 输入校验：金额必须为有限正数，币种和货币对有效，费率／事件参数在界内；未登录、未同意条款、`is_bot`、有负债买入、余额不足、池子暂停、储备不足、过期报价分别给出明确错误。
- 并发和恢复：同一用户并发订单不能透支；系统 tick 与玩家订单串行更新同一池子；进程在事务前、事务中或提交后重启都不会重复发布事件或重复扣款。FX 总闸和预算是最后一道可操作的止损手段。
- 数学测试：不同规模双向兑换、费用和 6 位舍入、无费往返无套利、同一市场多单价格冲击、系统预算与储备守恒、事件窗口速度和“玩家先推动价格则干预减少”。
- 集成测试：API 权限、管理员手动／定时事件、重启后补发且仅一次、`is_bot` 禁单、债务边界、净值和排行榜、审计重放、赛季重置。验证 Alembic 升降迁移、前端 type-check/lint、后端全套测试。

## 8. 实施顺序与明确非目标

实施按依赖推进：FX 模型与迁移 → AMM／钱包／审计 → 噪声及事件引擎 → 管理 API → 玩家 API／SSE → 资产口径 → 管理和玩家页面 → 赛季重置与完整验证。正式部署前 FX 总闸保持关闭，先用可重放模拟校准池子深度、事件冲击、反应时间和系统预算，再由管理员注资开市。

第一版不接真实汇率源，不提供外币兑外币、杠杆、卖空、限价单、用户做市、现有 PvE 或 quant 策略接入，也不允许管理员在开市后直接改写储备或已发布事件。

## 9. 不可变核心约束和实现门槛

以下约束是实现契约，不允许由后续任务自行解释、放宽或改名；若实现需要改变其中任何一条，必须先修改本 spec 和对应 plan，再继续编码。

### 9.1 资产守恒

对每个货币对，分别维护金圆券和外币的系统资产总量：

- 系统金圆券总量 = 池金圆券储备 `G` + 系统金圆券储备 `T_G`。
- 系统外币总量 = 池外币储备 `F` + 系统外币储备 `T_F`。
- 无手续费系统订单必须满足成交前后两个总量分别相等；系统订单的输入币种从 treasury 扣除，输出币种进入 treasury，不能同时把输入和输出都记入 treasury。
- 玩家订单只改变池储备、用户现金/钱包和手续费 treasury；每笔交易的前后快照必须能按币种重放并对账。
- `G>0`、`F>0`、`T_G>=0`、`T_F>=0`；任何 quote、预算或储备失败都不能提交部分状态。

### 9.2 预算和事件状态机

- 每日预算和事件预算均以成交前汇率折算的金圆券名义金额计量；卖出外币取得金圆券时也消耗金圆券预算。
- `event.parameter_snapshot["spent"]` 只能增加本事件实际成交的金圆券名义金额，不能用全局 daily spend 或配置预算覆盖。
- 事件发布必须在同一事务中完成：状态、参数快照、首轮成交、实际 spent、审计；首轮失败必须留下可提交的取消/失败状态和原因。
- 事件状态转换只能是 `draft -> scheduled -> published -> completed`，或 `draft/scheduled -> cancelled`；重复 publish 对已发布/完成事件返回原状态且不重复成交。
- 每个 pair 最多一个 published 事件；事件窗口结束、预算耗尽、储备不足或不可恢复 quote 失败必须完成/取消并写审计，不能永久卡在 published。

### 9.3 调度、恢复和公开边界

- 调度器只能使用一个进程级 engine 实例维护噪声时钟；数据库事件状态是恢复权威，重启后按 UTC 顺序处理到期事件。
- FX gate 关闭时，计划事件、噪声、常规干预和系统成交全部停止；只读 snapshot/chart/news 仍可用。
- 系统 tick 的单个 pair/event 失败必须通过 savepoint 或独立事务隔离，不能中止其他 pair，也不能提交半笔系统订单。
- 系统订单提交后才发布公开 frame；frame 只能含 `price`、`buy_price`、`sell_price`、`spread`、`volume` 和公开新闻字段。

### 9.4 实现前置门槛

任何引擎、事件或调度任务开始编码前，必须先有可运行的隔离数据库 fixture 和以下行为测试名：

- `test_system_move_conserves_each_currency_total`
- `test_system_move_respects_daily_and_event_budget`
- `test_tick_savepoint_failure_does_not_abort_other_pairs`
- `test_publish_event_records_first_trade_snapshot_and_is_idempotent`
- `test_publish_event_failure_persists_cancel_and_audit`
- `test_scheduler_processes_due_events_in_utc_order_and_honors_gate`
- `test_system_trade_publishes_only_after_commit`

只做 helper、source-string 或 tautological identity assertion 的测试不能作为 Task 5 或后续调度任务的完成证据。
