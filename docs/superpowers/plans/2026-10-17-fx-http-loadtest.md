## 限流方案（已确认方向，实施后由用户部署）

| 请求 | 限流键与额度 | 说明 |
| --- | --- | --- |
| FX 报价、成交及普通玩家写操作 | Bearer token，10 r/s，burst 20，nodelay | 覆盖现货、net、融资、short 和挂单写入，不遗漏嵌套路由；管理接口不进入此桶 |
| 已登录普通查询及 `/auth/me` | Bearer token，20 r/s，burst 40，nodelay | 不与同 Wi-Fi 下其他账户共享额度 |
| 匿名普通请求 | 真实客户端 IP，20 r/s，burst 40，nodelay | 无 Authorization 时必须回退 IP，不能使用空 key 意外免限流 |
| 登录、OAuth callback、refresh | 保留现有限制 | 本轮使用预签发 token；百人同时登录及刷新不在本轮验收结论内 |
| 管理接口 | 保留现有 api_admin 桶 | 管理 token 也不能误入普通玩家规则 |
| 公开市场行情 SSE | 同市场/IP 从 10 改为 200，市场总上限仍为 500 | 共用 limiter，LMSR 同样变为 200；私人账户流保持现有实现 |

只用现有 map/zone/location 结构与现有 limiter 常量，不新增用户额度存储。token 桶按 token 字符串区分，不宣称等价于严格按 user ID 防刷。

先核对 Nginx location 匹配优先级，确保 SSE 不被普通 FX 规则覆盖，仍关闭缓冲并保留长连接超时。真实 IP 沿用现有代理部署；如发现 CDN/代理识别不符，报告具体差异后单独决定，不通过伪造转发头模拟百人。

## 管理员脚本

新增 `backend/scripts/fx_loadtest.py`，只有本机 CLI，无 HTTP 路由。提供 `prepare`、`mint`、`inspect`、`cleanup` 四个子命令；输出本轮 manifest，将用户 ID、市场 ID、run ID 和临时状态记录到私有文件，不加数据库字段。

- `prepare --run-id <id> --users 100 --initial-cash 100000 --output-dir <private-dir>`：在维护窗口、停止经济写入后执行；通过 ORM 创建普通真人类型账户，`casdoor_id=loadtest:<run-id>:<序号>`，`is_superuser=false`、`is_bot=false`。不改已有用户，不调用 Casdoor，不启动第二个应用 owner 或调度器。
- 账户初始余额及审计注册记录遵循现有注册语义；测试账户可在明确测试用途下预置 TOS 接受时间，manifest 记录该事实，不修改正式注册要求。
- 使用专用测试 FX 市场，记录被暂时暂停的原交易市场。当前只允许一个 FX 市场处于交易状态，因此切换在维护窗口执行；测试参数以原市场的池子规模、费率和相关配置为基准，显式记录差异。不得直接借用 ID 8 成交后仅删除账户并声称原市场已还原。
- `mint --run-id <id> --output-dir <private-dir>`：复用 JWT payload/签发规则，仅给该轮普通测试账户签发短期 access token，建议有效期 60 分钟，不发 refresh token，不修改全站 token 有效期。必要时只对这批账户重新签发。
- 凭证文件权限 0600，目录 0700；日志不打印 JWT 或签名密钥。用户将凭证文件放到开发机，告知路径；manifest 可不含 token。
- `inspect --run-id <id>`：只读列出本轮用户、市场、关联表数量和待恢复状态；同 run 重复 prepare 不覆盖现有资金或市场。
- `cleanup --run-id <id> --dry-run` 默认只列清理对象；实际执行需明确该 run ID，且先停止压测和全部经济写入。按当前 FK 顺序事务删除该轮专用市场及账户的依赖记录，覆盖执行回执、成交、钱包、空仓、挂单、行情、清算、账本及审计引用，不复用旧 LMSR 删除 SQL。
- 清理关联按 manifest 中实际 ID 和本轮命名标记交叉核对，不仅靠模糊标题。发现其他账户参与测试市场等超出本轮的依赖时，先报告，不自行扩大删除范围。
- 清理后恢复准备阶段暂停的原市场状态；不覆盖其资产、池子、行情或期间无关配置。不执行 TRUNCATE、全库恢复或自动回滚整个业务库。
- 使用专用市场时，本轮系统事件和机器人是否作用于测试市场必须在开测前核对；记录实际开关，不把未启用的后台混合负载算作已测。若需要另改后台任务或生成一套市场参数，先提交具体选择。

## 负载与指标

建议新增 `loadtest/fx_http.py`，复用现有 httpx + asyncio；不模拟前端 DOM，不新增服务。每个测试账户最多一笔在途成交，独立 token、账户版本和请求编号。

| 阶段 | 负载 | 目的 |
| --- | --- | --- |
| 冒烟 | 1 人，60 秒 | TOS、账户上下文、报价、真实买卖、两类 SSE 首帧均有效 |
| 逐步升压 | 10 → 30 → 100 人，每档 60 秒 | 观察延迟和错误随人数变化 |
| 百人稳态 | 100 人，5 分钟；每人每 5–10 秒完成一次成交循环 | 名义目标约 10–20 次成交/秒；报告实际到达和成功率 |
| 集中下单 | 100 个独立账户在约 2 秒窗口内各提交一笔，随后观察 60 秒 | 看热点排队、尾延迟及恢复 |

以当前 FX 页面真实调用为准，优先使用 `/net/quote`、`/net/trades`、账户 context/version 和行情端点，不能只压旧现货捷径。普通资金交易不跨零、不借款；先买后按真实余额卖，避免大量余额不足请求占据测量。使用真实经济版本和每笔唯一 idempotency key，业务拒绝单独计数，不自动重试掩盖首次失败。

所有稳态在线账户各维持公开 FX SSE 和私人交易 SSE；账户版本检查沿用页面 15 秒节奏并错开起始时间。公开图表初次请求在入场时分散发送，不额外加入页面没有的高频轮询。

输出每阶段 JSON 汇总、每秒进度与请求样本，至少包括：

- 实际请求到达率、完成率、成功成交数/秒；达到的在线账户数、SSE 连接数和超出节奏的延迟，不能只报告目标人数。
- 报价、成交、账户读取各自的 P50/P95/P99；成功与失败延迟分开，保留各阶段，不能混成一个总分。
- 401/403、业务拒绝、版本冲突、429、5xx、连接错误和超时分别统计；解释未成交原因。
- SSE 建连到首个合法帧耗时、断连和重连次数；按关联事件检查成交后可见时间。无法可靠关联的推送只报告接收间隔/事件年龄，不宣称端到端广播耗时；跨机器时间比较标注时钟偏差。
- 不输出 token、Authorization header 或私人账户全量响应。结果保存在 `loadtest/results/<run-id>/`。
- 纯 HTTP 不提供 CPU、内存和数据库锁指标；用户若有现成监控可同步观察，不将安装监控作为前置条件。

开测前以成功 JSON 响应和合法 SSE 帧预检；1 人冒烟必须真实成交成功。运行中 401/403 立即停止；稳态滚动 30 秒内 429/5xx/超时合计超过 5%，或成交 P99 超过 2 秒，则停止增加负载、排空并报告。集中下单阶段单独标记峰值，不把预期排队混入稳态阈值。无自动重试队列或故障恢复流程。

## 扩充方案：常见 FX 热路径与具体负载

使用已有驱动、服务器 CLI 和生产 API，不新增框架、数据表或恢复机制。以下人数、频率和角色比例是本轮建议假设，不是现场统计。100 人同一公网 IP，集中争用一个测试交易池，维持 100 条公开 FX SSE 和 100 条私人账户 SSE。

### 1. 增补覆盖

- 入场读取：市场列表、公告、snapshot、账户 context、个人成交记录、等待中/已结束挂单列表；按实际组件记录市场列表的重复请求，不添加页面没有的周期轮询。
- 普通下单：继续用 `net/trades`，补齐成功后的账户 context、snapshot、个人成交记录刷新。私人事件触发的账户刷新与成交回调在短时间内合并，不每收到行情帧就刷一次账户。
- 报价：沿用生产服务端 quote，避免在 Python 复制前端 AMM/信用算法。每笔额外一次服务端 quote 的数量单列；主报告明确这是读取较重的场景，不能说与浏览器本地报价的 HTTP 数完全一致。
- 每 15 秒错开查询账户版本；只在版本响应要求补价格时请求 `trading-prices`，不将修复接口变成固定高频负载。
- 图表：按页面的封存历史段 + SSE 尾段加载；尾段新鲜时不机械请求 `/chart`，需要补尾时走相同时间窗的 `/chart`；少量用户切换一次周期，不全员频繁重读全历史。
- 初始市场是新建的，历史较浅；历史段路径可验证，但成熟大历史容量必须另用有历史的市场做只读测量，不能用空段替代其结论。本轮不复制生产账目或生成大型历史种子。
- 金融角色：60 个现金现货账户、20 个融资账户、20 个空头账户。使用真实小额成交准备相应持仓/债务，准备耗时单列，不计入稳态指标。
- 现金账户循环买卖；融资账户真实借入一部分预算买入，再卖出并覆盖自动还款路径；空头账户交替开空/回补，其中 5 个账户在预设步骤卖完多头再开空，覆盖两腿跨零成交。按当前页面分别使用 net 和 short quote/cover 接口，不为了覆盖接口额外走已不常用的旧入口。
- 初始小额建议为每笔 10–50 金圆券的预算/等值外币，融资借入其中 50%。具体金额在预检池子规模和费率后定，不用大单价格冲击制造大量业务拒绝；金额、初始资金和池子储备写入报告。
- 不自动打开贷款、做空或更改杠杆；预检记录真实开关和信用规则。缺开关则报告对应角色未测，不能悄悄用现货账户顶替并宣称混合场景通过。

### 2. 稳态强度与运行顺序

| 阶段 | 在线/交易安排 | 名义成交尝试率 | 建议观察时长 |
| --- | --- | ---: | ---: |
| 冒烟和角色准备 | 先 1 人验证页面链路，再逐个角色验证真实开仓/减仓；随后 100 人在 60 秒内入场 | 准备单单列 | 约 2–3 分钟，必要时以准备完成为准 |
| 只看行情 | 100 人在线，保留页面初始读取、SSE、15 秒版本检查，不主动成交 | 0/s | 2 分钟 |
| 正常游玩 | 40 人每 15–25 秒一笔，30 人每 45–75 秒一笔，30 人围观 | 40/20 + 30/60 = **2.5/s** | 5 分钟 |
| 活跃交易 | 70 人每 8–12 秒一笔，20 人每 30–50 秒一笔，10 人围观 | 70/10 + 20/40 = **7.5/s** | 5 分钟 |
| 加压 | 100 人每 3–5 秒一笔 | 100/4 = **25/s** | 2 分钟，异常可提前停止 |
| 集中下单 | 预先备好账户与报价，100 个账户在目标 2 秒窗口提交各一笔，买卖各约一半 | 目标 **50/s**，仅持续 2 秒 | 提交后观察 60 秒 |

稳态用户入组按 60/20/20 角色比例分层选取，避免活跃组恰好都是现金账户。频率基于实际尝试，不保证慢服务时达到名义值：每账户一笔在途，无追赶补发队列，同时报告实际开始率、成功成交率和晚于计划的时间。

100 人每 15 秒做一次版本查询，合计约 **6.7 个 HTTP 请求/秒**。驱动每笔暂按服务端 quote、成交、成交后 context、snapshot、个人成交记录共 **5 个 HTTP 请求**估算；图表需要 HTTP 补尾时再加 1 个。稳态预算约为：

| 强度 | 成交尝试/秒 | HTTP 预算（不含初始入场和 SSE 帧） |
| --- | ---: | ---: |
| 正常游玩 | 2.5 | 约 **19–22 请求/秒** |
| 活跃交易 | 7.5 | 约 **44–52 请求/秒** |
| 加压 | 25 | 约 **132–157 请求/秒** |

该预算只是解释负载的量级，不能替代实际统计：失败后不一定有完整刷新，做空接口组合、事件合并、价格修复和历史段读取都会改变请求数。当前浏览器主要本地报价，因而真实页面通常会少掉上表的一部分 quote HTTP 负载。

只读阶段还会有服务器自身的私人流定期身份/规则复核、行情广播等工作；200 条 SSE 长连接不折算成每秒 200 个 HTTP 请求。推送帧数、字节数与延迟单独统计。

集中下单与稳态分开：记录客户端实际提交窗口、到达节奏和请求排空时间，不把准备报价的耗时算成写接口排队，不把大量因行情变化拒绝的订单当成服务器成功承载。记录 60 秒恢复期的轻量读取响应；2 秒窗口是目标，不提前承诺实际会达到。

### 3. 小范围挂单场景

主稳态之外单跑约 2 分钟，不添加每账户轮询：

- 20 个账户各创建 1 张小额单，总计 20 张，低于现有每账户 3 张上限。
- 10 张在下一次扫描前撤销，其余 10 张选择满足条件的方向，使其在真实扫描中尝试成交；创建先覆盖撤销组，不假设撤单一定战胜调度器。
- 撤销组若已经触发，则如实记录，不能把真实状态竞争误归类为 API 性能失败。
- 观察订单扫描、实际执行、私人 `fx_order_result` 和页面列表/账户刷新；如轮次中未实际成交，报告该路径未覆盖。
- 记录实际扫描间隔，不为测试调快全站扫描配置。该场景不证明任意价位、跳价或停机期间追溯。

系统干预、PvE 混合与强平仍不作为本次默认新增场景；不能对未运行的后台负载给容量承诺。正常与活跃阶段通过后才进入加压及集中下单；保护阈值沿用原方案，失败不自动重试、不自动清理现场。

### Action 与凭证交付边界

只支持 owner 从 main 手动触发 inspect/prepare/mint/cleanup；prepare 和 cleanup 分别要求 PREPARE/CLEANUP，默认 inspect。与现有部署共用 `thccb-production` 互斥和 DEPLOY_HOST/USER/KEY；只读确认三个 secret 名称存在，没有读取其值或连接服务器。服务器必须先正常部署版本 fx-loadtest-2，workflow 不拉镜像、不替换 nginx、不部署应用。

开发机使用现有 cryptography 生成 RSA3072 密钥，私钥 0600 且目录必须在仓库之外。服务器以 RSA-OAEP(SHA256)封装 AES256-GCM 密钥，加密包含 60 分钟 JWT 的 JSON，成功写出加密文件后删除服务器明文。只上传固定 `credentials.enc.json` artifact，保留 1 天；开发机通过 gh 下载，并校验 run ID 后解密为 0600 文件。错误私钥和修改密文必须失败；不上传 .env、备份、私钥或明文 token。

工作流只写本轮接收公钥和加密文件；复用现有维护 wrapper 的停写、备份、恢复逻辑，不新增请求恢复或运维状态机。实际 SSH、Docker 维护和 Actions artifact 下载尚需用户上线后执行验证。
