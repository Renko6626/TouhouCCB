# 管理员 FX 页面优化实施计划

> 执行时使用 superpowers:subagent-driven-development（用户指定 Sol low 执行、Sol medium 审阅），按下列任务推进。本轮只更新计划，不执行代码修改、数据库迁移或部署。统一池子变化记录的架构已在对话中确认。

**目标：** 将市场登记与央行操作分开，让管理员按固定金额注资前看清状态、预计变化和玩家持仓，执行后可核对审计记录；注撤资形成的价格变化进入实时与持久 K 线。

**架构：** 资金权威仍为现有池子、钱包、金库、债务、成交与审计；新增 `fx_pool_event` 作为统一池子变化来源，在原资金事务里追加记录。改造现有增量行情游标、ring 和批量 flusher；不新增行情后台任务体系，不修改 AMM、借贷或强平规则。管理员页面沿用现有 Vue、FastAPI 与依赖。

**技术栈：** Vue 3 / TypeScript / 现有 UI；FastAPI / Pydantic / Decimal / SQLAlchemy。

**需求依据：** 本轮对话：第二条路线、默认固定金额、管理员简单执行与审计；已确认新增统一池子变化记录，并要求性能可控。随机波动机制留作后续独立决策。

## 范围与约束

- 默认输入金圆券、外币的固定数量；第一版不加入目标涨跌幅模式、比赛登记或自动结算。
- 保留现有注资／撤资同时调整交易池与系统金库的发行规则，预览中分别显示两份余额。
- 复用现有 POST fund / withdraw 与同事务审计；不新增幂等编号、执行任务或结果恢复机制。
- 页面提交中禁用操作；成功后显示执行结果，再独立刷新数据；刷新失败不能显示为执行失败。
- 网络异常导致结果不明时提示先刷新、核对操作记录，不自动重试资金请求。
- 预览表示当前快照的预计结果，不锁价、不保证固定涨跌幅；执行沿用现有锁内余额检查与最新储备。
- 固定金额注资可以在草稿、暂停或关闭的未归档市场执行，沿用现有规则；页面明确提示玩家当前可交易状态。
- 所有新接口仅超管可用；金额用 Decimal 和十进制字符串，遵守现有精度及存储范围。
- 页面验证最多截图，不自动点击、填表或跑浏览器交互流程；新增测试只覆盖真实新增行为。
- 注撤资不产生 FxTrade、成交量或成交笔数；成交仍沿原 AMM 曲线，注资仍改变池子规模，不用无限余额央行模拟成交。
- 公开行情事件不泄露储备、管理员身份、运营备注、审计内容或玩家私人数据。
- 本轮不加入模拟账户、随机任务、自动补币或活动自动执行；不加入回填临时磁盘暂存机制。

## 页面与接口方案

建议路由：`/admin/fx/markets`（市场登记）、`/admin/fx/operations`（央行操作）；旧 `/admin/fx` 重定向到登记页。管理入口保持一个，内部用页签切换；两页均展示交易总闸状态。

市场登记保留创建、编辑、状态管理、归档与删除。显示独立的只减仓状态，沿用现有 status / reduce_only 语义，不将暂停自动转成只减仓。

央行操作采用“当前状态 → 固定金额与预览 → 执行结果 → 最近操作记录”的布局。撤资作为次要入口。交易池、借币库存和手续费账户用自然中文名称，分别标注单位。

新增接口建议（均在现有 admin_fx 路由下）：

- `GET /pairs/{id}/overview`：当前币种、储备、金库、参考汇率、pool_version、as_of，以及玩家持仓汇总。
- `POST /pairs/{id}/liquidity-preview`：输入 `action: fund|withdraw` 与现有两种金额；只读返回操作前后池子／金库、参考汇率、涨跌幅、是否可执行及阻断原因；不写审计。
- `GET /pairs/{id}/liquidity-history?before_id=…&limit=20`：按审计 ID 倒序，过滤该币种 fx_fund / fx_withdraw，保留初始发行标记；返回时间、操作者 ID、数量、前后余额及可推导的汇率变化。

历史分页默认 20、最大 100，使用 keyset 而非深 OFFSET。持仓统计仅在进页、切币、手动刷新及操作成功后读取；预览采用 350ms 防抖，只读所选 pair／treasury，不触发持仓统计或风险估值。回执展示本次实际提交的池子状态，不把随后行情刷新当成本次操作的精确结果。

持仓第一版只提供多头人数／数量／成本、空头人数／本金／已入账利息／锁金。统计涵盖该币种全部钱包及空头记录，不默默排除机器人或停用账号；未实时计提的利息明确标注。多空分别聚合，避免联表乘积导致重复求和。暂不提供强平人数、全体平仓金额或全账户收益估算。

## 统一池子变化记录：存储与写入合同

新增 `FxPoolEvent` / `fx_pool_event`。它记录价格的真实来源，但不承担资金账务，也不是管理员执行任务表。

| 字段 | 定义 |
|---|---|
| id | BigInteger 自增主键，SQLite 使用 Integer variant；行情消费标识 |
| pair_id | 所属市场 |
| created_at | 该次变更的 UTC 生效时间，在现有品种锁内确定 |
| kind | initialize / trade / fund / withdraw |
| pre_gold_reserve、pre_foreign_reserve | 变更前两侧储备；initialize 为 NULL |
| post_gold_reserve、post_foreign_reserve | 变更后两侧储备，沿用 Numeric(16,6) |
| gold_volume | 成交买入=input、卖出=output；其他类型为 0 |
| trade_id | trade 关联真实 FxTrade；唯一、可空 |
| audit_id | initialize / fund / withdraw 关联审计；唯一、可空 |

约束：post 两侧为正，非 initialize 的 pre 两侧为正，volume 非负且非 trade 为零；trade 必须有 trade_id。initialize 以后价同时作为前后价，只建立有效历史起点。

索引：主键、来源唯一键、`(pair_id,id)` 用于增量追赶、`(pair_id,created_at,id)` 用于时间窗口与未覆盖事件检查。第一版不增加每日汇总表或 JSON资金快照。

写入同一个市场的事件沿用原 GATE／pair 行锁，原资金变更与记录原子提交。事件 ID在同市场内按锁内追加顺序消费，不要求全局 ID连续；不同市场交错 ID不会影响各自游标。同桶时间相同时用事件 ID判定顺序，不按网络到达顺序。`pool_version` 仍是报价依赖版本，不作为事件 ID，因为状态和参数编辑也会令它递增。

统一追加接口：`append_pool_event(db, *, pair_id, kind, created_at, pre_reserves, post_reserves, gold_volume, trade_id=None, audit_id=None)`，只添加 ORM记录，不 SELECT、不 commit、不新增锁、不计算持仓、不发布消息。

写入点与防重复边界：

- 创建市场：初始发行审计同事务追加 initialize。
- `fx/trading.py` 的实际现货／融资买入／现货强平执行点：真实腿追加 trade。
- `fx/shorts.py` 的实际开空／回补／空头强平执行点：真实腿追加 trade。
- net_trading、borrow_buy 和强平上层复用这些低层入口，不再重复追加。跨零两条腿对应两条事件，保留中间价格。
- `fx/liquidity.py`：注撤资与审计同事务追加 fund / withdraw。
- 幂等成交回放、失败、回滚、仅改金库、名称／状态／费率编辑不追加事件。
- 删除无成交的测试市场时，在既有清理事务删除其事件及派生行情；存在 initialize 或注资记录不等于有成交历史。资金审计保留，有成交的市场仍需归档。

成交复用现有 flush 后的 trade.id，事件 INSERT并入后续已有 flush／commit，不为获取 event.id 增加一条 SELECT或独立数据库往返。低频注资为取得 audit.id 必要时可 flush，不能将这种额外 flush复制进每笔成交。新增成本为每条真实腿一条 INSERT及索引维护，须实测，不声称无性能成本。

## K 线与实时行情合同

- 聚合保持 10s／1m／15m／1h。开盘=最早事件前价，收盘=最晚事件后价，高低包含全部事件前后价；初始化只贡献起点。
- 注撤资只贡献价格，volume=0、n_trades=0。新增 n_events，用于区分真实零量价格桶与合成空桶；n_trades 继续只统计真实成交。
- 同桶“成交 → 注资 → 成交”形成一根蜡烛，volume只含两笔真实成交。等比例注资可形成不改变价格的真实事件。
- 无事件周期在读取／前端补前收盘水平线，不后台逐周期写空桶。区间起点需要前价时，用有索引的最后有效历史锚点查询；新市场从 initialize 开始，旧历史无可靠锚点时不填当前价。
- FxMarketDataState 增加明确的 last_event_id，FxCandle 排序元数据改为 first／last event 标识并增加 n_events；旧 trade cursor 不能重新解释成 event cursor。
- candles＋last_event_id 继续同事务批量落库，重复批次不得重加 volume 或 n_events。保留现有单市场串行消费、失败重试、单写入者及有界 ring。
- HTTP chart、历史段、缓存完整性判断、bootstrap、SSE 重连与实时尾段统一使用事件源；窗口最大 ID、未覆盖事件检查和未落库补尾也必须改造，不能只修改聚合入口。
- 24h volume 的派生读取和 SQL回退保持真实成交口径；不能将注资金额计入 volume SUM。
- 公共 envelope 增加 `events: [{id,ts,pre_price,post_price,gold_volume,n_trades}]`；公开内容不必携带 kind／原始储备／audit_id／管理员字段。
- 覆盖字段使用 `history_tail_through_event_id`、HTTP `X-FX-Through-Event-ID`。尾段编码带 n_events；真实成交列表、私人记录和交易 API仍使用 FxTrade.id。
- 旧 trades 增量可在兼容过渡期保留，新图表只消费 events，避免一笔成交双重聚合；旧 through_trade_id 不填入事件 ID。新客户端缺新元数据时要求刷新到匹配版本，不假设覆盖完整。
- 前端 `fxCandle.ts` 不能继续用 v=0 判断真实空桶；使用事件计数／明确覆盖信息，信息不足则补尾，不能让后续成交抹掉已知注资 OHLC。
- envelope 模式只走事件路径；原价格 tick 仅在无 envelope 的既有模式下后备，禁止两路同时改写同根蜡烛。
- commit 后复用现有市场唤醒与 publisher。可合并最后价推送，但事件增量保留全部中间高低；缓冲溢出明确发 history_invalidated，客户端有界重读。
- 快照、事件尾段与覆盖游标同代且一致，接缝处的提交必须进入快照或随后增量，不能提前推进游标吞掉变化。上线重建时轮换 history_version，旧图表缓存不可继续复用。

## 性能约束与实际验证门槛

- 正常消费 SQL为 `WHERE pair_id=:pair AND id>:cursor ORDER BY id LIMIT 1000`，只投影聚合字段；不连接用户、审计 JSON或风险账户。
- 保留现有每 5 秒 reconciliation／批量 flush、RING_SPEC 的四档保留上限、512 条公共增量缓冲；新增事件不会新增定时逐币种价格采样任务。
- 单次后台 catch-up 最多 10 页（10,000 条）后重新排队，让其他品种和 flusher有机会运行。启动／离线回填可多轮处理，不能一次装入全部历史。
- 正常图表读物化 K 线／ring，只补 durable cursor之后且在请求窗口内的事件；不每次从成交和审计 JOIN／UNION 重算历史。
- HTTP及 SSE快照补尾上限 10,000 个未聚合事件，超出则明确返回可重试的历史未就绪状态，交给后台追赶；不能截断后宣称完整，也不在 GET路径无限 catch-up。
- 输出和细粒度源桶上限继续是 20,000；ring暖启动按每一档自己的保留窗口查询，不能加载最长期限的全部 10s数据再丢弃。
- 无订阅者时沿用 publisher跳过广播；不每个订阅者重复计算持仓／24h volume，不在注资请求里执行全体强平。
- 管理员预览与持仓读取分离；审计 keyset分页检查 PG执行计划。若旧索引会扫描大量其他市场记录，在同次迁移增加 `(ref_table,ref_id,event_type,id)`，只保留有查询依据的索引。
- 事件存储随真实操作数线性增加，不存每秒 tick或合成水平桶。第一版不自动删除原始事件；运维记录事件行数和表／索引大小，后续归档另行确认。
- 隔离 PostgreSQL对照普通成交、跨零成交、热点图表：相同数据与并发，至少 3 轮交替 before/after，记录吞吐中位数、p95、SQL／flush变化、事件和索引大小。旧报告引用的 `.superpowers/sdd/2026-10-12-fx-read-cost/throughput/runner.py` 在当前工作区已不存在，不能当作可直接运行的前提；优先恢复其已有夹具，恢复不到就用临时小脚本调用真实生产入口，复用现有 PG测试的隔离建库方式，不另建永久压测框架。产物放本任务临时目录，禁止覆盖旧报告或使用生产库。
- 成交吞吐中位数下降超过 10% 或 p95上升超过 15% 时先排查额外 flush／查询／索引，不直接宣布完成。这是排查门槛，未超过也不能宣称线上容量有保证。
- 用少量与较多历史记录的同一近端窗口查询对照和 EXPLAIN确认索引范围扫描，不随全历史规模线性读取。SQLite功能通过不能代替 PG性能证据；只做这次相关对照，不扩展全站压力测试。

## 历史迁移与恢复合同

- 新 Alembic revision新增事件表、event cursor、n_events及事件排序元数据；旧成交 ID、资金审计不重写。已有新价格事件的降级不能静默删历史。
- schema迁移不负责大批回填。扩展现有离线 rebuild工具，停止经济写入，取得原 ownership／pair gate，固定来源 cutoff，逐市场、固定页大小读取。按用户最新约定，沿用现有维护方式，不加入临时磁盘文件；核对后的规范化记录可暂存内存，当前数据量下接受这条低频离线路径的 O(N) 内存使用，不将它描述为总内存有界。正常在线行情仍须保持有界。
- FxTrade提供真实成交投影；有完整前后储备的 fx_fund／fx_withdraw审计提供人工变化；初始发行提供 initialize。
- 以真实时间和储备前后链核对跨来源顺序，再写统一事件；唯一 trade_id／audit_id保证续跑不重复。不能把导入顺序或任意来源优先级当作旧执行顺序。
- 同时间无法唯一确定顺序、审计缺字段或储备链断裂时，dry-run报告区间并拒绝标记“完整历史”。恢复取舍提交用户；不填当前价、零值或伪造旧事件。
- 回填后重建四档 K 线并轮换 history_version；初期 history_ready=false，核对来源数量、真实成交量和最终储备后置 ready。只读请求不承担全量修复。
- 原 CLI through-trade-id不得改成 event cutoff语义；新参数明确命名，旧参数作为旧来源筛选或明确报不支持。
- 只在可丢弃 SQLite／PG数据库验证升级、续跑、重建和重启。生产迁移／停机／部署／删历史／开市不在当前授权范围，后续单独安排。

## 需审阅的边界与限制

- 已确认统一池子变化记录与注撤资纳入 K 线；这版具体接口、迁移和性能门槛供用户审阅，当前只更新计划。
- 图表上的公开央行事件标签暂缓，价格蜡烛本身纳入本轮；无需披露操作身份才能显示真实走势。
- 不承诺网络异常下自动判断是否执行，也不承诺预览价与提交价相同；通过固定金额、审计核对和明确反馈满足离散运营操作。
- 持仓统计只展示基础库存与已入账债务；不将其作为实时风控或活动赔付依据。
- 验收重点：没有玩家成交也永久保留注资变化；零量不污染成交量；同桶、刷新、重启结果一致；近端图表不扫描全历史；新增写入成本有隔离 PG证据。
- 随机波动作为后续方案：优先考虑固定余额、有限频率与金额、默认不借贷的系统交易者，使用原成交入口。随机注资持续改变池子深度和金库，不作为普通噪声默认方案；系统账户统计、库存补充及开关另行确认。
