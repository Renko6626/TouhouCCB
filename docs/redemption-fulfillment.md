# 管理员线下核销

工作人员使用现有管理员账号，进入侧栏“兑换与称号 → 兑换码核销”，或从“兑换批次”行内的“查看 / 核销”进入。

列表提供全部兑换码、按码搜索（不区分大小写）、批次筛选、未售出/待核销/已核销筛选、每页 50 条分页和刷新。

只有已经购买且尚未核销的码可以确认核销。确认后显示核销时间、管理员和备注；重复或并发请求只会一次成功。用户“我的兑换”显示工作人员确认的“线下已兑换”，用户自己的已用备注不影响这个状态。

误操作可由管理员撤销，必须填写原因；撤销与重新核销都保留审计事件。撤销请求携带确认框打开时的核销时间，避免旧弹窗撤销后来重新核销的记录。

现场操作顺序：查找完整兑换码 → 核对购买人 → 核销成功 → 发放实物。搜索和操作都使用后端共享状态。

## 数据库升级

推送 `main` 后，CI/CD 会调用 `deploy/deploy.sh`；已有数据库会在重启后端前自动执行下面的迁移命令，正常自动部署不需要人工升级数据库：

```bash
python -m alembic upgrade head
```

迁移 `0d0ac23efa85` 增加 `redeemed_at`、`redeemed_by_admin_id`、`redemption_note`，保留原有库存、购买状态、余额和用户个人备注。旧码初始为未核销。应用的 `create_all` 不会给旧表补列，必须运行迁移。

本次开发只对 `/tmp/sunyunbo/` 内的独立测试数据库执行迁移，没有修改生产数据或部署配置。

## 接口

- `GET /api/v1/admin/redemption/codes`：管理员分页列表，参数 `batch_id`、`q`、`status`、`page`、`page_size`。
- `POST /api/v1/admin/redemption/codes/{id}/redeem`：`{"note":"可选备注"}`。
- `POST /api/v1/admin/redemption/codes/{id}/revoke`：`{"reason":"必填原因","expected_redeemed_at":"列表返回的核销时间"}`。

操作记录保存在 `audit_event`，事件类型 `redeem_fulfill`、`redeem_fulfill_revoke`，记录码 ID、批次、购买人、操作人、时间、备注/原因；撤销事件还保留被撤销核销的原始信息。

## 验证记录

新增 API 回归覆盖列表、筛选、字面搜索、分页、管理员权限、核销审计、重复/并发保护、个人备注独立、撤销原因、旧撤销确认冲突。迁移回归验证旧库存保留、升级、回退和再次升级。浏览器使用真实本地 API 验证桌面和 390 px 手机、核销/撤销、两个页面的旧状态冲突、用户状态，以及空/错误/重试。

正式发布工作区的完整后端测试：585 项通过、1 项原有跳过；核销与迁移相关回归 31 项通过、1 项跳过。前端 type-check、构建、44 项单测及本功能文件 lint 均通过。

仓库已有的全量 ESLint 问题仍保留，主要为旧 `any`、单词组件名和未使用变量；本次功能未新增错误，CI 使用类型检查和构建验证前端。
