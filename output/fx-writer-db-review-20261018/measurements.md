# 三组性能测量结果

三轮无 SQL 插桩容量实验的中位数；每场景每变体每轮 512 条命令，16 个账户。A 为只减少查询，B 为 A 加固定 SQL 结构复用。提升按吞吐中位数之比计算。

|场景|基线 commands/s|A commands/s|B commands/s|A 相对基线|B 相对基线|B 相对 A|
|---|---:|---:|---:|---:|---:|---:|
|现金净买入（1 pair）|205.46|204.89|208.18|-0.3%|+1.3%|+1.6%|
|融资净买入（1 pair）|147.44|150.28|159.53|+1.9%|+8.2%|+6.2%|
|旧融资买入（1 pair）|129.85|142.80|153.85|+10.0%|+18.5%|+7.7%|
|空头开仓/回补（1 pair）|158.02|172.12|182.96|+8.9%|+15.8%|+6.3%|
|融资净买入（4 pair）|195.90|205.80|229.65|+5.1%|+17.2%|+11.6%|

现金路径 A 没有减少查询，其 -0.3% 为噪声参照；B 的小幅变化与各轮区间重叠，不作确定收益承诺。融资净买入只省一条 SQL，A 收益有限；旧融资/空头省更多查询，A 的收益较明显。B 在融资、旧融资、空头和多 pair 场景保持同样 SQL 数，还能改善吞吐。

吞吐提高不等于所有尾延迟同步改善：现金路径 B 的 P99 高于基线；融资净买入 B 的 P99 也高于 A。这里只确认各场景所列的短时测量结果，不承诺 P99 全面下降。

## 诊断轮提交占比与较大改造的上限

只看单 pair 基线；每场景 64 个带诊断命令。SQL、显式 flush 与 handler 的 span 相互包含，不能相加。COMMIT 客户端耗时包括响应/调度，不能视为 WAL 纯执行成本。

|场景|handler mean ms|cursor elapsed ms/笔|显式 flush ms/笔|commit ms/笔|commit/handler|假设完全消除 commit 的理想吞吐上限增幅|
|---|---:|---:|---:|---:|---:|---:|
|现金净买入（1 pair）|5.004|1.827|2.188|0.563|11.3%|12.7%|
|融资净买入（1 pair）|6.998|2.539|2.924|0.590|8.4%|9.2%|
|旧融资买入（1 pair）|8.293|2.804|1.755|0.621|7.5%|8.1%|
|空头开仓/回补（1 pair）|6.433|2.242|1.764|0.575|8.9%|9.8%|

这个上限只是假设其余工作不变、提交阶段凭空消失的单 pair 模型，不能当 group commit 的实测收益。真实批处理保留耐久提交、等待凑批、错误隔离和快照安装，收益通常小于该理想值；多 pair 的提交还会重叠。当前数据不支持优先为 group commit 重写事务语义。

正式实验合计 24,000 条测量命令，其中无 SQL 插桩容量轮 23,040 条；60 个场景/变体进程全部完成，无业务/基础设施错误，资金与历史断言全部通过。预热命令另外计，不纳入容量分母。

每个变体在所有正式轮中的 app 源码 SHA256 映射完全一致。原始数据见 [raw/summary.json](raw/summary.json)，执行方式和限制见 [report.md](report.md)。
